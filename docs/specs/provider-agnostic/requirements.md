# provider-agnostic — требования

Дата: 2026-10-29. Статус: Draft (ожидает approve).
Предшественники: `docs/specs/hybrid-providers` (OpenRouter, ADR-14),
`docs/specs/hybrid-local` (fastembed, ADR-17). ADR-18 в
`docs/specs/docsbase-memory-mcp/design.md`.

## Задача

Сегодня провайдер hybrid-ступеней — это набор `match name` в четырёх местах:
сборка стейджей (`from_config` знает про OpenRouter, а local — через
`local::embedder`), `provider_status`, `connect` (два раздельных флоу) и
`resolve_embedding`/`resolve_reranker` (валидация каждого провайдера инлайном).
В `src/` и `tests/` 51 жёсткая ссылка на имя провайдера, пять мест перечисляют
обоих провайдеров парой. Добавление третьего провайдера (второго remote —
Ollama, OpenAI-совместимый, что угодно) требует правок в ~10 местах, в том числе
в парсинге конфига и в справке CLI.

Цель: провайдер становится **данными** (запись в таблице), а не ветвлением.
Добавление провайдера — новый модуль + одна строка в таблице. UX единый для
всех провайдеров; единственное исключение — скачивание моделей, оно есть только
у провайдера с локальным кэшем.

## Цели

- **G1.** Единая адресация модели: `<provider>/<model>` во всех местах, где
  пользователь или конфиг называет модель.
- **G2.** Провайдер как данные: одна таблица `&'static dyn Provider`; никаких
  `match` по имени провайдера в продуктивном коде.
- **G3.** Единый UX: `connect`, `models use`, `models list` (и статус в
  `docsbase status`) работают одинаково для любого провайдера.
- **G4.** Дешёвое расширение: «добавить провайдера» не трогает
  `config.rs`/`cli/*` — только новый модуль и строка регистрации.

## Не-цели

- **NG1.** Абстракция HTTP-диалектов (OpenAI-совместимый слой, Cohere/Jina
  схемы). Делаем шов, а не преждевременную универсализацию: пока второго
  remote-провайдера нет, общий HTTP-клиент не проектируем (YAGNI).
- **NG2.** Слияние `hybrid::local` и `hybrid::openrouter` в один модуль: у них
  разные возможности (инференс+провижининг против HTTP-клиента), их объединяет
  только контракт стейджа и он уже общий.
- **NG3.** Унификация скачивания моделей: `models fetch`/`models remove` остаются
  операциями провайдера с локальным кэшем; требование единого UX означает
  единый *адрес* и понятный отказ для провайдера без кэша, а не «скачивание
  через OpenRouter».
- **NG4.** Новые крейты.

## Функциональные требования

- **FR-1 (must) Адрес модели.** `<provider>/<model>`: провайдер — сегмент до
  первого `/`, модель — остаток строки без изменений (идентификаторы remote-моделей
  сами содержат `/`: `openrouter/nvidia/nemotron-3-embed-1b:free`). Пустой
  сегмент, пустая модель, неизвестный провайдер → Admission с перечнем известных
  провайдеров и примером корректного адреса.
- **FR-2 (must) Голых имён нет.** Ни в одной команде `models use|fetch|remove`
  имя без `<provider>/` не разрешается по каталогу и не выводится из реестра.
  Ошибка обязана содержать исправленную команду целиком.
- **FR-3 (must) Конфиг.** `[providers.<name>]` и `provider`+`model` в
  `[hybrid.embedding]`/`[hybrid.reranker]` сохраняют текущую TOML-форму: адрес
  существует только на границе CLI. Файлы пользователей не требуют миграции.
- **FR-4 (must) Внутренняя модель конфига.** Записи провайдеров хранятся
  generic-контейнером (имя → запись), а не полями `fastembed`/`openrouter`;
  разбор и валидация записи делегированы самому провайдеру. Коды ошибок
  объявлены явно: неизвестное имя провайдера в конфиге → `Admission` со списком
  известных имён (как сегодня); незнакомый ключ внутри известного провайдера →
  `Admission` с именем провайдера и его допустимыми ключами (сегодня это
  `Internal` из serde); ключ, который сегодня молча отбрасывается
  (`[providers.openrouter] runtime = "…"`), после изменения отвергается так же.
  Разбор конфига **не зависит от build-фич**: файл, записанный сборкой с
  `hybrid-local`, обязан читаться дефолтной сборкой, а гейт срабатывает при
  сборке стейджа, а не при парсинге.
- **FR-5 (must) Реестр провайдеров.** Одна таблица; поиск по имени; перечисление
  для UX. Провайдер объявляет: имя, требуемую build-фичу (если есть), статус
  готовности, разбор своей записи конфига, разрешение своей стадии
  (`model`/`dims`/`normalize`, `window`), сборку обеих стейджей одним вызовом
  (чтобы делить дорогие ресурсы), опциональный каталог моделей. Таблица
  **не гейтится фичами**: в любой сборке зарегистрированы все известные
  провайдеры, а фича ограничивает только *использование* (FR-4). Провижининг в
  реестре не объявляется — он целиком в CLI-слое (FR-8).
- **FR-6 (must) Сборка стейджей.** `from_config` только находит провайдера и
  вызывает его билдеры. Спецлогики конкретного провайдера в `from_config` нет.
- **FR-7 (must) Статус и список.** `provider_status` и `models list` печатают
  строки таблицы провайдеров; набор колонок одинаков, содержимое
  провайдер-специфично и приходит из записи провайдера (версия, путь, причина).
- **FR-8 (must) Единый `connect`.** `connect <provider> [--check] [--force]`:
  одинаковые флаги и одинаковый каркас (проверка → запись провайдера → печать
  результата → подсказка про рестарт) для всех провайдеров; тело проверки и
  установки — у провайдера. Семантика едина и объявлена: `--check` — отчёт без
  записи в конфиг; без флагов — проверка и запись; `--force` — повторная
  проверка и перезапись (у провайдера с установкой — переустановка);
  `--check --force` — `Admission` с одним и тем же текстом для всех. Тело
  провижининга живёт в CLI-слое, ядро его не видит; каркас принимает
  провижинера параметром, чтобы тест мог подставить фейка.
- **FR-9 (must) Каталог.** Провайдер с закрытым каталогом (локальный реестр)
  объявляет его и показывает в `models list` полными адресами; провайдер без
  каталога строк не даёт, но остаётся адресуемым.
- **FR-10 (must) Расширяемость доказана тестом.** Третий провайдер, объявленный
  целиком в тестовом модуле, проходит через сборку стейджей, статус, разбор
  адреса и каркас `connect --check` **в процессе** — через параметр таблицы и
  параметр провижинера, без правок продуктивного кода и без подмены глобалов
  (`#[cfg(test)]`-элементы недоступны спавнящемуся бинарю).
- **FR-11 (must) Совместимость поведения.** Не меняются: значения
  `EmbeddingCfg`/`RerankerCfg` из конфига, canonical `model_id` (кэш векторов и
  ANN остаются валидными), тексты `feature_missing_remote`/`feature_missing_local`,
  и поведение поиска/индексации. Меняются **сознательно и перечислены здесь**:
  печатные таблицы (`models list`, `connect --check`) показывают полный адрес;
  ошибки, где в тексте появляется адрес модели, получают префикс провайдера;
  тексты «unknown provider» перечисляют имена из реестра, а не статическую пару.
  Правки фикстур, которые конструируют `ProvidersCfg` полями
  (`src/hybrid/config.rs:895,945`, `tests/hybrid_config.rs`) и вызывают голые
  имена (`tests/cli_models.rs`), ожидаемы и входят в задачи T3/T4.

- **FR-12 (must) Разделение адреса при записи конфига.** CLI разрезает адрес по
  первому `/` и пишет в конфиг `provider` и **остаток** (модель как есть):
  `openrouter/nvidia/nemotron-3-embed-1b:free` → `provider = "openrouter"`,
  `model = "nvidia/nemotron-3-embed-1b:free"`. Полный адрес в поле `model`
  запрещён — он испортил бы canonical `model_id` и инвалидировал кэш.
  Пустой остаток (`openrouter/`) — `Admission`. Проверяется `models use
  --dry-run`.

## Нефункциональные требования

- **NFR-1.** Дефолтная сборка остаётся офлайн: таблица провайдеров в дефолтной
  сборке содержит только записи, не тянущие сетевые/ML-крейты; гейт `cargo tree`
  не меняется.
- **NFR-2.** Число мест, которые надо тронуть для нового провайдера: ≤ 2 файла
  (новый модуль + одна строка регистрации) + документация. Проверяется
  ревью-чеклистом, а не метрикой.
- **NFR-3.** Никаких `unwrap`/`expect`/`panic!` в `src/**`; все отказы —
  `Error::Admission` с одним корректным действием.
- **NFR-4.** Сообщения об ошибках адресации не выдают внутренних имён
  (`Some(...)`, `ProviderState::…`) — только CLI-термины.

## Критерии приёмки

1. `docsbase models use embed fastembed/bge-small-en-v1.5` и
   `docsbase models use embed openrouter/nvidia/nemotron-3-embed-1b:free --dims 2048`
   пишут идентичные по форме конфиги (различие — только значения).
2. `docsbase models use embed bge-small-en-v1.5` → Admission с полной
   исправленной командой.
3. `docsbase connect openrouter --check` и `docsbase connect fastembed --check`
   печатают одну таблицу с одинаковыми колонками.
4. `rg -n 'PROVIDER_FASTEMBED|PROVIDER_OPENROUTER' src/` даёт совпадения только
   в объявлениях модулей-провайдеров и в таблице регистрации.
5. Тест с фейковым третьим провайдером зелёный; его модуль не трогает
   `config.rs`/`cli/*`.
6. Все существующие suite-тесты зелёные без правок ожидаемого поведения
   (кроме тестов, где адрес модели стал обязательным — они правятся по FR-2).
