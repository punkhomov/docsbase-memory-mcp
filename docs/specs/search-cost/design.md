# Search Cost — Design (phase 1)

> Спек: `requirements.md`. Задачи: `tasks.md`.

## 1. Где живёт кэш

`DenseCache` (`src/hybrid/dense.rs`) уже владеет состоянием тира (entries,
generation, digests, outcomes) и уже проброшен в единственный шов поиска
(`search_docs_with`) и в бенчмарк. Поэтому кэш вектора запроса — поле этого
структуры, а не новый слой демона:

```rust
struct QueryCache {
    entries: HashMap<QueryKey, (Arc<[f32]>, u64)>,   // key → (vector, bytes)
    order:   VecDeque<QueryKey>,                     // LRU: front = coldest
    bytes:   u64,
    hits:    u64,
    misses:  u64,
}
type QueryKey = (String, String);                    // (model_id, blake3(text))
```

`VecDeque` вместо отдельного timestamp'а: порядок обновляется на попадании
(`remove` + `push_back`), вытеснение берёт `front`. 256 записей — это микрометры
на операции, поэтому O(n) `position` не проблема.

## 2. Почему ключ без проекта

Вектор запроса — чистая функция от `(model_id, text)`: `model_id` пинит провайдера,
модель, размерность и версию нормализации, а роль-префикс (`embed_query`) статичен
для модели. Проект в ключ не входит, иначе один и тот же вопрос в двух проектах
платил бы дважды.

## 3. Промах не вставляет

`query_vector` только читает и считает hit/miss. Вставка — отдельный
`store_query_vector`, который вызывает код **после** успешного `embed_query`.
Поэтому ошибка провайдера не может осесть в кэше под видом вектора.

## 4. Наблюдаемость

`status.query_cache = {hits, misses, entries, bytes}` — глобально, потому что ключ
не проектный. `None` (CLI direct-режим, тесты) отдаёт нули: это «не вижу кэш
демона», а не «кэш выключен».

## 5. Бенчмарк: делиться только кэшем запросов

`run_config_timed` создаёт `DenseCache::new()` на каждую конфигурацию — так замер
холодного скана остаётся честным. Если отдать конфигурациям общий `DenseCache`,
прогреются ещё и строки чанков, и латентность перестанет быть холодной.

Поэтому `DenseCache::sharing_query_cache()` возвращает кэш со свежими
entries/digests/outcomes, но **общим** `query_cache`, а
`run_config_timed_with_query_cache(..., Some(&cache))` использует его. Live-прогон
создаёт такой кэш один раз, и вторая dense-конфигурация получает вектора запросов
даром — целевые 193 вызова вместо 386.

## 6. Чего дизайн не делает

- **Single-flight нет.** Два одновременных одинаковых запроса оба промахнутся и оба
  заплатят. Корректность не страдает (оба получат один и тот же вектор), поэтому
  это отложено; при надобности — карта in-flight по ключу.
- **TTL нет:** вектор не устаревает.
- **Персистентности нет:** кэш пересчитывается заново после рестарта демона, это
  дешевле валидации на диске.
- **Кэша результатов нет** и не будет: он устаревает при любой правке файлов.
