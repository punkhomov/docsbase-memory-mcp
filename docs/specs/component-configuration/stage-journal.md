# Журнал подготовки и замены файла конфигурации

2026-11-24, CF5b2b. Формат предназначен для миграции при остановленных потребителях.
Сейчас команда миграции выдаёт план. Описанный ниже протокол проверяют на отдельных
БД и временных файлах в нативных тестах.

## Что хранится до первой замены

В **новой приватной БД** создать [базовые таблицы](control-state-v1.sql) и
[расширение формата 2](control-stages-v2.sql) в одной транзакции. Параметры
соединения заданы в [контракте управления](control-contract.md). При ошибке
откатить транзакцию полностью. Расширение проверяет версию и отсутствие записей.
Заполненный журнал v1 сохраняет прежний формат и требует отдельного восстановления.

До запечатывания операции каждому источнику соответствует неизменяемая запись.
Для отсутствующего файла поля образа равны SQL NULL. Для существующего исходного
файла сохраняется ID объекта. Один профиль описывает атрибуты до и после замены.

| Поле | Кодирование |
|---|---|
| ID объекта | Идентификатор тома или устройства (8 байт), затем ID объекта (16 байт), оба little-endian. Unix inode расширяется нулями, в Windows используется полный 128-битный ID, как в планировщике. |
| `unix-stat-v1` | Три u32 little-endian: UID, GID и биты прав и специальных режимов (`mode & 07777`). |
| `windows-attributes-v1` | Маска файловых атрибутов Win32, u32 little-endian. |

На исходный ID и оба набора атрибутов приходится до 48 байт на источник. Ещё
по 24 байта могут занимать ID двух опубликованных файлов. Для 257 источников это
до 24 672 байт самих ID и атрибутов без накладных расходов SQLite. Имя временного
файла выводится из ID операции, номера источника и направления. Для байтов, путей
и размера БД продолжают действовать пределы базового формата. Содержимое журнала
доступно только владельцу приватного хранилища.

В Unix этот профиль не охватывает ACL, xattrs и платформенные флаги. В Windows
он не охватывает дескриптор безопасности и альтернативные потоки. До включения
записи владелец должен определить допустимые атрибуты целевого хранилища,
сохранять все необходимые для восстановления данные в заданных пределах и связать
их с проверенным планом и согласием пользователя. Текущий CLI эти атрибуты в план
не включает.

## Порядок записи и повторного запуска

1. Под блокировками остановленной установки зафиксировать запись о намерении
   до создания временного файла. Она ссылается на запечатанный источник и
   направление. Источник задаёт операцию, родительский каталог, байты и атрибуты.
   Для применения используется образ «после», для восстановления — «до».
   Возврат к отсутствующему исходному файлу требует отдельной операции удаления.
2. В удерживаемом каталоге создать файл с вычисленным именем, исключительным
   созданием и приватными правами. Записать данные в пределах лимита. До замены
   целевого файла однократно зафиксировать ID подготовленного объекта. После сбоя
   имя может уже существовать при ещё пустом поле ID. На поддерживаемом Linux такой
   интервал можно сократить, подготовив безымянный файл.
3. После любой попытки замены проверить фактическое состояние каталога. Сверить
   байты, допустимые атрибуты, принадлежность объекта и подтверждение записи на
   носитель. Только затем установить `published=1`. Триггер в том же SQL-операторе
   фиксирует прогресс источника. Опубликованный ID сохраняется для восстановления.
   Незавершённая запись блокирует смену направления, завершение операции и отметку
   источника как проверенного. Сам SQL не может подтвердить сброс каталога на диск.
4. При повторном запуске сначала обследовать существующую запись. Отозвать её
   до публикации можно только после независимой проверки первоначального состояния
   цели и отсутствия нерешённых временных или резервных файлов. Повторная попытка
   использует то же имя. При неоднозначности сохранить файл и запись до явного
   разрешения. Опубликованные записи хранятся до очистки после восстановления v1.
   Во всей операции одновременно допускается одна незавершённая замена; на один
   источник приходится не более двух записей за оба направления.

## Наблюдение после сбоя

[Запрос чтения](inspect-stage-v2.sql) получает ID операции, номер источника,
направление, проверенные ID каталога и профиль, а также состояние обоих имён.
Для обычного файла с одной жёсткой ссылкой передаются ID, хеш байтов и базовые
атрибуты. Подтверждённое отсутствие — `missing` и три NULL. Ошибка чтения, ссылка,
неподдерживаемые атрибуты или нестабильное наблюдение — `unavailable`. При
устаревшем ключе запрос возвращает ноль строк. Это требует новой проверки.

| Результат | Что наблюдалось |
|---|---|
| `previous_target_stage_absent` | Цель совпадает с предыдущим образом, включая ожидаемое отсутствие. Временного имени нет. |
| `previous_target_stage_matches` | Цель совпадает с предыдущим образом. У временного файла совпали сохранённые ID, байты и атрибуты. |
| `target_matches_stage_absent` | Временного имени нет, цель совпадает с подготовленным объектом. Сбой всё ещё мог предшествовать записи прогресса или сбросу каталога на диск. |
| `inspect_required` | Например, временное имя существует без записанного ID, обнаружена другая цель, не совпали атрибуты или чтение не удалось. |

При восстановлении прежнее состояние существующей применённой цели сверяется с ID,
сохранённым при публикации. После закрытия дескрипторов файловая система может
снова выдать тот же ID. Для удаления, замены или фиксации конечного состояния нужны
отдельные доказательства принадлежности и долговечности.

Нативные Rust-тесты открывают журнал в режиме чтения после выхода дочернего процесса
без деструкторов в четырёх точках. Проверяются реальные файлы и SQLite, несовпадение
прав и байтов, посторонний объект с теми же байтами, ограничения формата и переход
к восстановлению. Проверка потери питания и полного сохранения атрибутов входит
в CF5b2c.

Ограничение одной незавершённой записи использует уникальный частичный индекс.
Дополнительная проверка перед INSERT защищает прежнюю запись при REPLACE и
отключённых рекурсивных триггерах. [Конфликты SQLite](https://sqlite.org/lang_conflict.html)
и [частичные индексы](https://sqlite.org/partialindex.html).


## Delta 2026-11-24 — базовый профиль в плане

Планировщик теперь использует кодирование из таблицы выше. В JSON виден только
хеш предусловия. Изменения UID/GID/режима Unix или маски атрибутов Windows
учитываются при повторном чтении и при сравнении планов. Полный допуск к замене
файла по-прежнему требует проверки хранилища и дополнительных атрибутов.
