# Публикация поколений индекса

ADR для CF10. Перед включением CF11 нужны проверки границ записи и удаления
на целевых ОС. Рецепты и идентичности артефактов определяют их владельцы в CF8,
CF9 и CF13. Этот контракт задаёт способ связать их с данными на диске.

## Текущая граница

В `store/migrations.rs` общая SQLite содержит реестр, jobs, документы и
чанки. `lifecycle::index_dir` вычисляет единственный путь Tantivy для проекта.
`index::job` фиксирует маркеры pending, коммитит Tantivy, затем обновляет
документы и generation в SQLite. Разрыв между этими операциями виден через
pending/rebuild. `tools::in_read_phase` использует revision и файловую lease
на коротких фазах. Перед сетевым ожиданием поиск владеет уже скопированным
payload. Это позволяет отказать одному проекту при неполной записи и
продолжить обслуживать остальные.

Смена рецепта должна готовить новое состояние отдельно. Две транзакции SQLite
и Tantivy не дают атомарного переключения. Для `ATTACH` в WAL SQLite
гарантирует атомарность отдельной БД, а не совокупности. Общая точка публикации
будет хранить один указатель на уже готовые артефакты. [SQLite WAL](https://www.sqlite.org/wal.html).

## Выбор размещения

Рассмотрены два варианта полной замены.

| Размещение | Граница записи | Цена удаления старого поколения |
|---|---|---|
| Строки обоих поколений в общей SQLite | Копирование и переиндексация строк занимают общий writer. WAL удерживается самым старым SQL-читателем | Удаление освобождает страницы для повторного использования. Уменьшение файла требует дополнительной работы |
| Отдельная SQLite метаданных на поколение проекта | Подготовительный writer изолирован. В общей БД остаются короткие операции с указателем и журналом | Файлы целиком удаляются после закрытия всех соединений и отображений в память |

Выбрана SQLite метаданных на поколение для полной замены. Пробный скрипт
создаёт 20 000 документов и 80 000 чанков по 600 байт в схеме из
`store/migrations.rs`. Базовая БД занимает 55,3 МиБ. Вариант общей БД копирует
строки под вторым ключом проекта и меняет 400 чанков. Прежний reader удерживает
WAL. Изолированный вариант копирует отдельную SQLite через Backup API и
обновляет те же 400 чанков в rollback journal.

| Linux, SQLite 3.46.1, три запуска | Медиана подготовки | Суммарный размер файлов, наблюдённый до освобождения прежнего состояния |
|---|---:|---:|
| Общая БД | 253 мс (244–261) | 111,3 МиБ, включая WAL 55,9 МиБ |
| Две БД | 132 мс (130–134) | 112,2 МиБ, включая журнал 1,6 МиБ |

Разница в задержке относится к скопированным метаданным на этой машине.
Измерение не включает первый экспорт из общего реестра, Tantivy, векторы,
дисковый барьер каталога и холодный page cache. Размеры измерены в точках,
указанных в скрипте. Размер transient файлов в рабочем executor входит в
бюджет независимо от этого прогона. [Проба](experiments/storage_copy.py) ·
[SQLite Backup API](https://www.sqlite.org/backup.html) ·
[sqlite3_backup_step](https://www.sqlite.org/c3ref/backup_finish.html).

При первом переходе экспортируется только выбранный проект, порциями под
согласованным SQL-снимком и рабочим дедлайном. Копировать общий реестр через
Backup API для этого перехода нельзя. Если уже есть отдельная БД проекта,
Backup API — кандидат для metadata reuse при полном rebuild. Продолжительность
копирования ограничена исходной операцией. При записи в источник со стороны
другого соединения SQLite может начать копирование заново. Перед публикацией
всё равно сверяются исходный указатель и ревизия.

Обычные sync и watcher пишут в текущее поколение без полной копии. Пока оно
текущее, действует прежняя короткая граница чтения и pending recovery.
Вытесненное поколение больше не получает записей. Оно обслуживает уже
захваченные чтения до освобождения их ресурсов. Смена BM25/query policy или
ANN traversal использует тот же индекс. Изменение ANN construction готовит
граф по его собственному рецепту. Смена tokenizer может требовать новый
Tantivy, при этом подготовка использует прежние проверенные строки и vector
keys. Полная замена в первом executor может физически скопировать пригодные
строки напрямую без разбора исходников и повторных вызовов провайдера.

## Схема, имена и идентичности

Реестр `registry.db` получает новую основную версию `PRAGMA user_version`.
Существующие бинарники проверяют её при открытии. У живых SQLite handles нет
такой повторной проверки. Поэтому первый переход выполняется при остановленных
daemon, CLI writers и library owners. Установочный барьер должен исключить
новый legacy writer до изменения схемы. Capability новых клиентов проверяется
до допуска к операциям с generation layout. Для старого бинарника требуется
явный offline переход с закрытием уже открытых handles. Если остановка
не подтверждается, переход отклоняется. Перед изменением схемы контроллер
сохраняет проверенный SQLite backup по действующей maintenance policy.
После остановки до commit восстановится прежняя версия. Восстановление backup
после commit требует остановки и восстановления связанной пары данных, чтобы
старый реестр не открыл файлы новой эпохи. Поддерживаемый restore выдаёт
новый идентификатор эпохи установки до допуска запросов. Ручной откат файлов
в обход остановленного restore не входит в этот контракт.

Следующие поля образуют минимальный контракт.

| Таблица | Ключ и поля |
|---|---|
| `generation_store` | Одна строка с форматом и 128-битной эпохой из системного источника случайности. Сброс cache root и поддерживаемый restore создают новую эпоху после проверки состояния и до допуска запросов |
| `project_generation_head` | `project_id` PK, `active_id` NOT NULL. Пара `(project_id, active_id)` ссылается на строку своего проекта. Проекты без индекса допускают отсутствие head |
| `project_generations` | `id INTEGER PRIMARY KEY AUTOINCREMENT`, `project_id`, уникальная пара `(project_id, id)`, `layout` из legacy/local, `phase` из building/sealed/active/retired/reclaiming, `base_id` nullable, `base_revision`, `plan_id`, `seal_digest` nullable, `reserved_disk_bytes`. Не более одного staging на проект |

Переходы фаз ограничивает SQL транзакция. Единственная запись active
соответствует head. Ссылки на base хранятся как значения предусловия, чтобы
retired можно было удалить. Запись head и записи phase обеих сторон
обновляются одной транзакцией. Отложенный FK пары учитывает и требуемую
active phase. Частичные уникальные индексы разрешают одну active и одну
building/sealed запись на проект. Scratch SQL проверил отказ при ссылке
на чужой проект или sealed и при отдельном переводе текущей строки в retired.
Монотонный идентификатор поколения остаётся уникальным в cache root после сброса одного проекта. Идентичность запроса
включает регистрационный проект, generation id и ревизию содержимого.
В новом layout локальный `generation_state` в `metadata.db` содержит id
поколения, project id и возрастающую ревизию содержимого. Текущий writer
меняет metadata, pending и revision в одной локальной БД. Head при обычном
инкременте не меняется. SQL-читатель держит project read lease, пока совмещает
head со snapshot данных. Legacy `projects.index_generation` служит исходной
ревизией для первого перехода.

Миграция реестра присваивает существующей индексной паре запись legacy и head,
сохраняя файлы и строки. Метаданные legacy находятся в общей SQLite, Tantivy в
`projects/<project-id>/tantivy/`, а lease их физических читателей в
стабильной `.legacy-generation.lock` внутри папки проекта. Подмена переводит
legacy запись в retired одновременно с новой local записью. Reclaim ждёт
закрытия её handles, удаляет прежний Tantivy и транзакционно очищает строки
этого проекта в общем реестре. Удаление строк увеличивает freelist. Фактически
выделенный размер `registry.db` и его WAL учитывается один раз до физического
уменьшения. Автоматический VACUUM в apply не входит.

В `projects/<project-id>/generations/<id>/` находятся `metadata.db`,
`tantivy/`, `.read.lock` и `seal.json`. Пути выводятся только из проверенных
числовых идентификаторов и фиксированных имён. Директория создаётся сразу
под своим новым именем с приватными правами. Её открытие поиском разрешает
только head. `seal.json` содержит версию формата, проект и id, версию схемы
metadata, канонические несекретные идентичности метаданных и лексического
рецепта, основание сборки и список имён и размеров файлов в пределах
существующего state byte limit. Для обещанного hybrid seal включает рецепт
document embeddings, требуемое coverage, привязку graph recipe и digest
набора chunk id/hash, если ANN обязателен. Реестр связывает seal его digest
и фиксирует несекретную identity принятого плана и ревизии настроек. Ни
credentials, ни произвольные пути в descriptor не попадают.
Проверка полного инвентаря файлов из seal выполняется для staging до CAS.
После публикации этот инвентарь хранит факт первоначальной сборки. Текущий
Tantivy manifest и локальная SQLite проверяются по своей ревизии, pending
и требуемым рецептам. Проверка опубликованного поколения не опирается на
инвентарь seal даже при той же content revision. Например, no-op sync
может коммитить Tantivy и инициировать merge без изменения content revision.

Текущий `chunk_id` кодирует `(doc_id, seq)`. Сохранённые строки могут
сохранить это значение. Прежний числовой `read_neighbors` сохраняет свой
wire contract и читает текущее состояние с обычной read lease. Он не
подтверждает, что между двумя вызовами ничего не изменилось.

Новый маршрут progressive disclosure объявляет отдельную capability.
Клиент явно просит `chunk_ref` в search и передаёт его в новый
`read_neighbors_at`. Токен хранит версию, эпоху установки, проект,
generation id, content revision и исходный chunk id. Проверка токена
и lookup проходят под одним read lease. Другой epoch, проект, revision
или generation дают typed retry. Числовые поля и прежние вызовы остаются
доступными с текущей семантикой. Нативные потребители MCP, IPC,
TypeScript и `ask_docs` используют новый маршрут при его наличии. Проверка
после restore должна отвергать ссылку даже при совпадении всех числовых
полей. `get_doc` читает живой Markdown. Snapshot связывает сохранённые id,
текст, metadata и snippets в одном индексном запросе. [MCP tools](../../MCP.md).

## Подготовка и publication

Онлайн commit выполняет владелец работающего daemon. CLI передаёт ему
принятый план через negotiated команду. Direct apply допустим в stopped
maintenance с эксклюзивным управлением установкой. При запуске daemon и
при прямом поиске разрешённые настройки сравниваются с active seal и
релевантными recipe identities. При несовпадении требуемого артефакта
старый head не совмещается с новым runtime. Значения query-only с теми же
artifact recipes могут измениться через обычный reload. Pins и доступность
требуемых vectors проверяются при связывании. Seal сам по себе не доказывает,
что общий cache не вытеснил записи после публикации.

1. Зарезервировать staging для проекта по стабильной `.prepare.lock` и записать
   building в реестре до создания файлов. Удерживать резервацию до завершения
   физической работы. Короткая согласованная read phase фиксирует base
   pointer, revision и отсутствие pending/rebuild в SQLite и Tantivy до
   чтения metadata. Весь исходный metadata snapshot проверяется и
   копируется согласованно. Обнаруженное неполное состояние допускается
   только явным recovery plan с полным пересозданием необходимых входов.
   Фиксируются также approved plan и upstream identities. Writer локален для
   staging и не удерживает общий write transaction, project read/write lease
   или соединение реестра на provider wait.
2. Материализовать согласованные SQLite и Tantivy. В Tantivy нужен явный
   fallible finish с ожиданием merge threads. Текущий `IndexHandle::drop`
   предупреждает об ошибке и недостаточен для seal. Закрыть SQLite writer и
   снять его journal/WAL посредством успешного commit/checkpoint, без
   ручного удаления sidecar. Сверить generation и набор id между обоими
   хранилищами, проверить артефакты по выбранному рецепту. Если план допускает
   degraded lexical, опциональный ANN можно построить позже. Для обещанного
   hybrid состояния проверяются требуемые vectors и pins прежде, чем принять
   sealed. Векторы остаются content-addressed в общем VectorStore.
3. Записать seal, синхронизировать данные и имена на поддерживаемом хранилище,
   затем записать sealed с digest в реестре. На Linux синхронизация файлов
   дополняется синхронизацией содержащих каталогов и новых родителей.
   Для macOS нужно проверить подходящий full-flush режим, для Windows
   отдельно доказать порядок сохранения путей и содержимого на поддержанных
   локальных томах. Flush открытого файла в Windows подтверждает его данные.
   Доказательство сохранения родительских имён требует отдельной нативной
   проверки. [Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html) ·
   [Microsoft FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) ·
   [SQLite fullfsync](https://www.sqlite.org/pragma.html#pragma_fullfsync).
4. До publication проверить снимок Markdown против исходного наблюдения.
   Зафиксированные события watcher, новый revision или отличия при rescan
   приводят к stale. Зафиксировать watermark перед сверкой и проверить его
   перед commit. События после последней сверки проходят через обычную
   очередь и разбираются новым writer. Markdown внешнего редактора имеет
   грань наблюдения, а не файловую транзакцию с SQLite.
   Для финальной сверки взять source locks по путям, общим с
   `config::paths::with_config_write_lock`. Фиксированный порядок global →
   project, затем project reload и publication authority. Попробовать
   взять `.writer.lock` эксклюзивно. При busy отпустить guards до ожидания.
   Активный job может держать writer lease и ещё потребовать
   `ProjectCell::preparation_lease`. Сверить актуальные source identities,
   watermark, registry head, content revision, отсутствие pending и phase.
   Удерживать source guard через CAS, чтобы корректно упорядочить
   поддерживаемые config writers. Внешний редактор может изменить файл
   после проверки. Runtime публикует ровно принятый снимок, а новый source
   требует нового разрешения.
5. Durable SQLite commit заменяет указатель и фиксирует обе фазы.
   Для WAL управляющее соединение проверяет `synchronous=FULL` или более
   сильный режим. Успешный commit предшествует ответу. Daemon меняет подготовленные config/stages и
   generation handle до освобождения локальной publication authority.
   Читатель либо получает всю старую пару, либо всю новую. Межпроцессное
   чтение валидирует тот же head под проектной lease. Ошибка commit с
   неизвестным результатом требует повторного чтения durable head перед
   выдачей и удалением файлов.

### Проба границы commit

В изолированном Linux-прогоне два обычных вызова CLI index создали разные
SQLite/Tantivy пары. Scratch registry в режиме WAL и с synchronous FULL
содержал один указатель. Остановка процесса через SIGKILL после UPDATE до
commit оставила head 1. Остановка после commit до ответа оставила head 2.
В обоих случаях CLI search в выбранном cache нашёл только свой документ.
Открытая read-транзакция прежней SQLite сохранила значения. Проба проверяет
процессную границу commit и пригодность обеих пар. Падение питания и
продуктовое подключение указателя остаются отдельными проверками CF11.

## Читатели, восстановление и бюджет

Новый читатель захватывает текущий generation и совместимую ревизию под
проектной read lease. Короткий доступ SQL/Tantivy держит `.read.lock` в
shared mode. Reload защищает выбор пары config/stages. Блокировки БД и
файлового проекта завершаются до сети. Ресурс, которому физически требуется
старый mmap или connection, удерживает поколение до закрытия. Если поиск
продолжает работу с готовым payload, он освобождает файловый lease и сохраняет
свой байтовый бюджет. Для повторного чтения после сетевой стадии требуется
совместимый id/revision, иначе возвращается существующая retry семантика.
Старый фоновой worker допускается к локальному кэшу по идентичности артефакта
и сверяет current authority перед публикацией для проекта.

Startup recovery берёт ту же `.prepare.lock`, что и live staging, прежде
чем проверять и удалять незавершённые работы. При занятой lease работа
остаётся зарезервированной и учитывается. Cleanup берёт project coordination,
убеждается в retired, получает
эксклюзивный `.read.lock` и переводит запись в reclaiming. Новые читатели
уже исключены. Закрывает handles перед удалением на Windows. При ошибке
удаления, включая препятствующий mapping, сохраняет запись и байтовый charge
до следующей попытки. Удаление directory entries должно пройти тот же
нативный барьер устойчивости имени, что и создание. Только после
подтверждённого барьера можно удалить reclaim record и снять физический
charge. При прерывании наличие и принадлежность проверяются заново.
Незнакомые файлы и каталоги без подтверждённой принадлежности не удаляются.
Пути не переиспользуются.

| Точка остановки | Действие при следующем запуске |
|---|---|
| До building | Сохранить прежний head |
| Building, артефакты частичны или seal отсутствует | Проверить принадлежность по записи и подтверждённой папке, освободить незанятую staging после аварии |
| Файлы готовы, sealed не записан | Указатель прежний. Обращаться со staging как с незавершённой подготовкой |
| Sealed, транзакция head не зафиксирована | Сохранить старую выдачу. Прерванное применение не получает автоматического согласия на публикацию |
| Commit прерван или ответ утерян | Один прочитанный head определяет результат. Проверить ссылку на артефакт до сервиса |
| Head новый, старый handle жив | Служить новому, retain старый до завершения reader |
| Reclaiming, удалена только часть | После проверки ownership повторить удаление. Повторный ранний запуск сохраняет charge |
| Head указывает на отсутствующий или несовместимый артефакт | Отклонить затронутый проект с диагностикой. Сохранить данные и retired запись для явного восстановления |

Разрешённый владелец бюджета учитывает active, staging, retired, reclaiming,
журналы и времена жизни физических workers. Изменение reservation сверяется
и до запуска, и при расширении staging. Технический отказ в записи или ENOSPC
не переиспользует имя текущего состояния. RAM учитывает writer/merge,
соединения, captured payload, vector pins и graph work вместе с живыми
старшими handles. Окончательный расчёт порогов и применимые типы томов требуют
измерения и native gates. Проба выше показывает цену копии metadata, а
не её полный ресурсный максимум.

## Последовательность CF11

- **CF11a:** versioned registry head, общий accessor для metadata/Tantivy и
  старого layout, no-write observation. Числовые пути, validator, миграция
  реестра без перемещения пользовательских данных и тесты обоих layouts.
- **CF11b:** частная подготовка и sealing с реальным SQLite/Tantivy. Режим
  без publication позволяет проверить физический бюджет, явный finish,
  конечность copy и очистку незавершённого staging. Воспроизвести остановку
  до и после каждого sync и seal, нативные барьеры на Linux, macOS, Windows.
- **CF11c:** CAS публикации и единый snapshot поиска в daemon и direct CLI.
  Проверить остановку на commit, неуспех revalidate, гонку с инкрементом и
  reload, mismatch старых ids нового текста, повторный запрос при смене
  ревизии. Проверить неизменную legacy выдачу, токены нового маршрута
  через MCP/IPC и ask_docs, и отказ прежних токенов после restore.
- **CF11d:** recovery startup, reclaim под cross-process leases, peak usage
  с reader, mapping и worker cancellation. Проверить отказ при снижении
  лимита, последующую очистку и действия CLI с настоящим approved plan.
  Только после этого проверять SC-4 на применимых типах хранилищ.

Граница совместимости старого формата конфигурации описана отдельно.
Первичное принятие нового storage layout — осознанное действие с доказанной
готовностью предыдущего индекса. Библиотечные и maintenance потребители
сверяют версию до получения writer.

## Delta 2026-11-25 — общий резерв остановленной подготовки

Транзакция SQLite, которая записывает building, суммирует резервы building,
sealed и reclaiming локальных поколений для всей установки. Сумма вместе с
новым запросом должна помещаться в доступные байты тома кандидата. Резервы
считаются целиком, в том числе когда временные файлы уже заняли часть места.
Активные и retired артефакты входят в наблюдаемое занятие диска. Отказ
сохраняет существующие записи, и попытка может повториться после discard.

Этот допуск координирует владельцев одной SQLite. Физический лимит на записи
временных SQLite и Tantivy файлов требует отдельного ограничения в writer.
Объём и действия сторонних процессов зависят от файловой системы.

## Delta 2026-11-25 — освобождение retired local поколения

Остановленный библиотечный вызов принимает ID retired поколения и исходный
запрос подготовки. Он сверяет базовое поколение, ревизию, исходный резерв,
parent intent и owner marker, затем получает эксклюзивную lease читателей.
Для неизменяемой остановленной пары принадлежность и размеры уцелевших
файлов подтверждает seal. Переход в reclaiming предшествует удалению.
Seal остаётся до устойчивого удаления payload, после чего повтор допускает
только owner marker. Каталог освобождает резерв после устойчивого удаления
пары и intent. Активный указатель проверяется в обеих SQL-операциях. Режим
поддерживается на файловых системах с подтверждаемой синхронизацией каталогов.
Для будущих инкрементально изменяемых поколений нужен инвентарь на момент
вывода из эксплуатации.

## Delta 2026-11-26 — предел записи остановленной лексической пары

Резерв учитывает оба ownership record. Новый SQLite-файл создаётся с
`max_page_count`, вычисленным из остатка резерва и размера страницы. У
частной базы нет предыдущего полезного состояния: неудачная сборка подлежит
discard. Журнал отключён только на изолированном writer, временные таблицы
и сортировки остаются в памяти. Сборка SQLite с принудительным дисковым
temp store отклоняется. Writer закрывается до формирования Tantivy.

Tantivy получает остаток после измерения закрытого SQLite-файла. Общий счётчик
списывает байты до записи сегмента или временного файла атомарной замены.
Удаление сегмента не возвращает charge, пока сборка может удерживать mmap.
Это консервативный предел суммарно принятых байтов. Он может отклонить
сборку, чей финальный размер был бы меньше резерва. Уцелевшие writer и
directory handles держат файловую lease, даже если один worker уже вернул
ошибку. Seal по-прежнему проверяется вместе с сохранёнными файлами перед
записью.

Дисковый предел относится к длинам файлов пары и её ownership records.
Файловая система отдельно учитывает блоки и служебные записи, реестр ведёт
собственные транзакции. Этот этап касается остановленной подготовки.

## Delta 2026-11-26 — прямой лексический читатель

Обычный `docsbase search` может открыть ранее опубликованную пару v5.
Каждая краткая фаза выбирает активное поколение под проектной блокировкой
и держит файловую аренду выбранного поколения до конца чтения Tantivy.
SQLite открывается read-only в пределах занятого слота. Локальная пара
использует epoch, ID проекта и поколения, content revision и digest seal.
Выдача и фрагменты проверяют эту identity при каждом повторном чтении.

В записи seal проверяются формат, identity, схема и рецепт. Рецепт должен
совпасть с полным результатом локальной индексации и разрешённой конфигурацией
запроса. Несовпадение останавливает поиск. Зарегистрированные legacy-пары
остаются на прежнем пути SQLite/Tantivy под той же блокировкой.

Для опубликованной неизменяемой пары сверяются имена и длины компонентов
Tantivy из seal. Служебный reader lock исключён из этой сверки. При допуске
инкрементальных writers для таких пар потребуется текущая identity Tantivy.

Прямое открытие WAL-реестра использует стандартный SQLite read-only и может
оставить пустой WAL/SHM. Остановленная подготовка сохраняет прежнюю проверку
sidecars. При их наличии можно явно повторить публикацию с тем же
утверждённым запросом и квитанцией, чтобы SQLite восстановил реестр перед
следующей подготовкой. Штатное создание реестра v5, hybrid и daemon
по-прежнему требуют отдельной активации.
