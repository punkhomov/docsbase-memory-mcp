# Search Quality — Requirements (SPECIFICATION)

> Feature: `search-quality` (S1–S6 из `docs/search-quality-research.md` §5).
> Контекст продукта: `docs/specs/docsbase-memory-mcp/{requirements,design}.md`,
> принципы: `docs/specs/constitution.md` (1.2.0), исследование:
> `docs/search-quality-research.md`.
> Hybrid-стадии (S7) — отдельный спек `hybrid-search` (не в этом документе).

## 1. Problem

Догфудинг v0.1.0-alpha.3 на собственном репозитории показал четыре дефекта качества
поиска, которые делают лексическую ветку хуже, чем она должна быть:

1. **Морфология RU не покрыта.** `замены`/`заменой` дают 0 хитов, `замена` — score 1;
   `каталогов` — 1, `каталоги` — 4. EN тоже страдает (`replace` находится,
   `replaced`/`replacement` — нет). Причина: точный матч токенов без стемминга.
2. **Гранулярность чанков.** Секции без подзаголовков превращаются в omnibus-чанки
   (пример: `progress.md:261–333`, 73 строки, ~3345 слов) — они слабо матчатся на
   почти любой запрос (score 2–6) и дают бесполезную цитату; cap чанка задан в
   **байтах** (`MAX_CHUNK_CHARS=4000`), для русского текста это ≈2000 букв — вдвое
   строже, чем для английского.
3. **Позиции токенов.** Каждый синонимичный вариант identifier-токенайзера
   (`raw` → `trimmed` → `alnum_runs` → `camel_split`) получает новую позицию:
   `assessment_plan_id` → 4 позиции; фраза `"plan id"` ложно матчит один `_`-токен,
   а настоящие соседние фразы могут не находиться.
4. **Нет триггера пересборки.** `open_or_create` сверяет только имена полей +
   `REBUILD_MARKER`; смена токенайзера/нормализации молча оставит старый индекс.

Дополнительно: у проекта нет объективных метрик качества поиска — любое «улучшение»
недоказуемо (существующие `tests/search_golden.rs` фиксируют 4 кейса, все EN).

## 2. Goals / Non-goals

**Goals**
- G1: объективные golden-метрики (recall@k/nDCG) и зафиксированный baseline.
- G2: точные цитаты: чанк ограниченного размера + рекурсивный структурный сплит.
- G3: корректные позиции токенов (фразовые запросы) и обязательный rebuild при
  смене токенайзера.
- G4: RU/EN морфология через мульти-токены без потери exact-матча идентификаторов.
- G5: тюнинг бустов/penalty по метрикам (без форка tantivy).
- G6 (P3): базовая искомость CJK и Unicode-нормализация без словарей и новых крейтов.

**Non-goals**
- Hybrid/embeddings/сеть (S7, ADR-13) — отдельный спек `hybrid-search`.
- Тюнинг BM25 `k1/b` (hardcoded в tantivy 0.26; только форк — отклонено).
- Semantic chunking, LLM-контекстуализация, late chunking.
- Словарная сегментация CJK/Thai (lindera/jieba) и reranker — из-за словарей/бюджета.
- Изменение публичных контрактов MCP/CLI (формы ответов `search_docs`/`docsbase search`).

## 3. Users / Actors

- **Coding-агент** (основной): вызывает MCP `search_docs`/`get_doc`/`read_neighbors`,
  ожидает точную цитату и нахождение по любой словоформе.
- **CLI-пользователь**: `docsbase search`, `docsbase index/sync/status`.
- **Владелец/мейнтейнер**: принимает изменения по golden-метрикам, следит за
  схемой/пересборкой.

## 4. Prioritized user stories

### P1 — S1: Golden baseline и метрики
**As** владелец проекта, **I want** видеть recall@k/nDCG на фиксированном корпусе,
**so that** каждое изменение принималось или отклонялось по цифрам, а не по вкусу.

- **Why P1:** без baseline все последующие шаги недоказуемы; S1 — вход для S4/S5.
- **Independent test:** тестовый harness печатает/фиксирует метрики до изменений.
- **Acceptance scenarios:**
  - Given golden-корпус и список запросов с ожидаемыми top-k, When harness считается,
    Then отчёт содержит recall@k и nDCG для каждого запроса и агрегат.
  - Given baseline зафиксирован, When прогоняется без изменений кода, Then метрики
    совпадают (детерминизм).
  - Given target-кейс (RU-форма), When он не находится, Then он помечен как failing —
    это вход для S4.

### P1 — S2: Chunk cap и единицы
**As** пользователь docs, **I want** цитаты, указывающие на конкретный раздел,
**so that** результат поиска не отправлял меня в 70 строк «свалки».

- **Why P1:** устраняет главный источник мусорных совпадений; влияет на цитаты и
  будущие эмбеддинги.
- **Independent test:** для секции без подзаголовков все прозаические чанки ≤ cap
  (атомарные fence/table — исключение, SC-5); цитаты точные.
- **Acceptance scenarios:**
  - Given секция 3000 слов без подзаголовков, When идёт индексация, Then ни один
    прозаический чанк не превышает cap + overlap; срез — по границе токена
    (идентификатор не рвётся), аварийный посимвольный срез — только для
    безпробельного блоба длиннее cap без границ; атомарные fence/table — исключение
    (SC-5 delta, SQ15).
  - Given RU-документ, When считается cap, Then лимит не вдвое строже EN при равном
    числе символов (единицы нормализованы).
  - Given сплит по абзацам/строкам списка, When строится цитата, Then
    `line_start/line_end` указывают на исходные строки файла.

### P1 — S3: Позиции токенов и tokenizer_version
**As** пользователь, **I want** фразовые запросы без ложных матчей и без молча
устаревшего индекса, **so that** `"plan id"` не матчит `assessment_plan_id`, а смена
анализатора не оставляет старые результаты.

- **Why P1:** ложные фразовые матчи — прямая неверная выдача; версия — защита от
  silent stale index при S4/S6.
- **Independent test:** тест токенайзера на позиции + тест rebuild при смене версии.
- **Acceptance scenarios:**
  - Given `assessment_plan_id` в документе, When запрос `"plan id"` (фраза), Then
    документ НЕ матчится; When запрос `assessment_plan_id`, Then матчится.
  - Given настоящая фраза `plan id` в тексте, When фразовый запрос, Then находится.
  - Given индекс, собранный с tokenizer_version=N, When открывается сборкой с N+1,
    Then индекс помечается на rebuild и старый не читается молча.

### P1 — S4: RU/EN стемминг мульти-токенами
**As** русскоязычный пользователь, **I want** находить документы по любой словоформе,
**so that** «замена» и «заменой» находят одно и то же, не ломая exact-матч
идентификаторов.

- **Why P1:** главный измеримый прирост качества (литература: десятки процентов MAP).
- **Independent test:** target-кейсы S1 по RU-формам переходят в passing; SC-1
  golden не регрессирует.
- **Acceptance scenarios:**
  - Given документ со словом «замена», When запрос `замены` или `заменой`, Then
    документ находится в top-k.
  - Given идентификатор `MAX_FRAME_BYTES`/`assessment_plan_id`, When запрос точным
    идентификатором, Then он находится (стемминг его не сломал).
  - Given стемминг включён, When поиск EN-запросов из golden-кейсов продукта
    (SC-1…SC-4 docsbase), Then релевантные документы остаются в top-k
    (hit@k no-regression).

### P2 — S5: Тюнинг бустов/penalty по метрикам
**As** мейнтейнер, **I want** выбирать бусты полей и `LONG_CHUNK_PENALTY` по golden,
**so that** точность растёт без форка tantivy.

- **Why P2:** полезно, но вторично после S1–S4; k1/b недоступны.
- **Independent test:** значения зафиксированы и обоснованы отчётом метрик.
- **Acceptance scenarios:**
  - Given два набора бустов, When прогон на golden, Then выбранный набор не хуже
    baseline ни на одном кейсе и лучше хотя бы на одном.

### P3 — S6: Мультиязычный слой (CJK, Arabic, Unicode-фолдинг)
**As** пользователь смешанных доков, **I want** базовую искомость CJK и нормализацию
Unicode, **so that** китайский/японский текст и арабика находятся без словарей и без
выхода за бюджет 40 MiB.

- **Why P3:** не блокирует v1.x; закрывает «хвост» языков дёшево.
- **Independent test:** CJK-запрос находится биграммами; Arabic с harakat находит
  документ без них; ё/width-варианты находят друг друга.
- **Acceptance scenarios:**
  - Given CJK-текст без пробелов, When CJK-запрос, Then документ находится (биграммы,
    корректные позиции).
  - Given арабское слово с harakat в документе, When запрос без harakat, Then
    документ находится.
  - Given «ёлка» в документе, When запрос `елка`, Then документ находится.

## 5. Functional requirements

- **FR-1** (must) Golden-harness: расширяемый корпус (fixture) + набор запросов с
  ожидаемыми top-k; считает recall@k и nDCG; результат — отчёт с порогами
  (recall@k дискретен, nDCG с округлением/толерансом; float-снапшот хрупок
  поперёк платформ).
- **FR-2** (must) Target-кейсы: RU-формы (`замена/замены/заменой`,
  `каталоги/каталогов`), идентификаторы (`assessment_plan_id`, `MAX_FRAME_BYTES`),
  фразовые (`"plan id"` vs `assessment_plan_id`), заготовки CJK/Arabic.
- **FR-3** (must) No-regression gate: выпадение релевантных документов из top-k
  golden-кейсов продукта (SC-1…SC-4 docsbase — top-k-ассерты, hit@k по классам)
  отклоняет изменение; исключение — осознанное обновление снапшотов **цитат**
  при S2 (delta). Точные ранги/скоры могут меняться при смене корпуса (новый
  сплит → новые чанки → новые BM25-скоры) — критерий presence, не равенство.
  *(MODIFIED SQ15: delta покрывает и дрейф хвостовых позиций — документы ниже
  per-case top-k-ассертов могут меняться, не только координаты цитат
  chunk_id/lines; критерий приёмки — hit@k per-case, а не неизменность набора.)*
- **FR-4** (must) Chunk cap: лимит размера чанка в нормализованных единицах
  (chars с замером конверсии; целевой эквивалент ≈300–500 токенов), рекурсивный
  сплит: заголовок → абзацы → строки списка, overlap ≈10%.
- **FR-5** (must) Единицы: cap и `text_len`/penalty считаются в одной единице;
  для RU/EN лимит эквивалентен по числу символов.
- **FR-6** (must) Цитаты: `line_start/line_end` после сплита указывают на исходные
  строки; `read_neighbors` продолжает работать (соседние чанки того же документа).
- **FR-7** (must) Позиции: все варианты одного исходного токена (raw/trimmed/alnum/
  camel/стем) занимают одну позицию (синоним-семантика), поэтому фразовые запросы
  ведут себя как при единственном варианте: ложных матчей нет, настоящие фразы
  находятся.
- **FR-8** (must) `tokenizer_version`: версия токенайзера/нормализации учитывается
  рядом с индексом; несовпадение → rebuild-маркер, старый индекс не читается молча;
  индекс — производные данные, миграция выполняется полным rebuild из SQLite.
- **FR-9** (must) RU/EN стемминг мульти-токенами: Snowball (`Language::Russian`,
  `Language::English`); стем-вариант standalone-слова **заменяет** поверхностную
  форму (tantivy трактует multi-token литерал как PhraseQuery, same-offset термы —
  конъюнкция, поэтому raw+стем не даёт кросс-форменного матча; Ruling SQ7);
  идентификаторы сохраняют точные токены (FR-10).
- **FR-10** (must) Защита идентификаторов: токены с `_`, CamelCase, ALL_CAPS,
  цифрами не стеммятся (keyword-marker-правило).
- **FR-11** (should) Тюнинг: бусты полей и `LONG_CHUNK_PENALTY` выбираются по
  golden-метрикам и документируются.
- **FR-12** (may) CJK: script-aware эмиссия биграмм с корректными позициями, без
  словарей и новых крейтов.
- **FR-13** (may) Arabic: нормализация (harakat/tatweel/hamza-формы) + встроенный
  Snowball Arabic.
- **FR-14** (may) Unicode-фолдинг: ё→е, width folding (полно/полуширинные), full
  case folding (подмножество `nfkc_cf`), Turkish İ/I — минимально, без нового крейта
  (крейт `unicode-normalization` — только через ADR, см. Open questions).
- **FR-15** (must) Офлайн-дефолт не меняется: никаких сетевых крейтов в дефолтной
  сборке; SC-8 продукта остаётся зелёным.
- **FR-16** (should) Гигиена токенов: токены длиннее лимита (≈40 символов) не
  индексируются (аналог `RemoveLongFilter`) — защита терм-словаря от безпробельных
  блобов (находка code-ревью).

## 6. Non-functional requirements

- **NFR-1 Performance.** Поиск p95 ≤ 200 мс при ≤ 50 000 чанков и индекс 1 000 md
  ≤ 30 с — не хуже текущих значений (замер до/после; стемминг/биграммы увеличивают
  индекс, регресс по latency недопустим). Рост размера индекса/памяти — в пределах
  бюджета продукта (замер RSS); для CJK-корпуса latency замеряется отдельно
  (биграммы ≈×2 токенов).
- **NFR-2 Maintainability.** Схема индекса версионируется; смена анализатора →
  автоматический полный reindex; каждый FR покрыт автотестом.
- **NFR-3 Portability.** Linux x86_64 и Windows x64: CI зелёный; новых крейтов нет
  (кроме решения по `unicode-normalization` через ADR).
- **NFR-4 Reliability.** Один writer и crash-safety не нарушаются; rebuild
  идемпотентен (повторный запуск не портит индекс).
- **NFR-5 Security/Privacy.** Ноль сетевых запросов в дефолтной конфигурации; логи
  без содержимого документов (конституция 1.2.0, NFR-5 продукта).
- **NFR-6 Quality evidence.** Каждое изменение качества сопровождается замером на
  golden (recall@k/nDCG) до/после; «улучшение» без цифр не принимается.
  *(SQ15: sweep/тюнинг параметров валиден только на дискриминирующем корпусе;
  на сатурированном golden результат фиксируется как «варианты неразличимы» —
  урок SQ8.)*

## 7. Data model

- **Chunk (индекс):** `chunk_id` (doc_id<<32|seq), `doc_id`, `text`, `title`,
  `heading_path`, `text_len` (в нормализованных единицах), `line_start/line_end`.
  Сплит может увеличить число чанков; `seq` перенумеровывается.
- **Golden fixture:** корпус `.md` + запросы `{query, expected: [(path, rank)]}` +
  метрики `{recall@k, nDCG}`; расширяется RU/CJK/Arabic документами.
- **tokenizer_version:** целое, рядом с определением токенайзера; участвует в
  проверке при открытии индекса (аналог `REBUILD_MARKER`-условия).
- **Baseline:** зафиксированные значения метрик (отчёт с порогами) как эталон S4/S5.

## 8. Interfaces

- MCP `search_docs {query, limit}` → `{path, heading_path, lines, score}` — форма
  не меняется; цитаты становятся точнее.
- MCP `read_neighbors {chunk_id, before, after}` — семантика не меняется.
- CLI `docsbase index|sync|search` — поведение и флаги не меняются.
- Тестовые: `cargo test --test search_golden` (метрики/кейсы),
  `cargo test --test tokenizer` (позиции), rebuild-тест (версия).
- Конфиг: новых пользовательских ключей нет (cap — внутренняя константа,
  документируется; экспозиция в конфиг — вне скоупа).

## 9. Measurable success criteria

- **SC-1** Baseline: метрики (recall@k/nDCG + per-query) зафиксированы до изменений
  и воспроизводимы (детерминизм).
- **SC-2** RU-формы: `замены`/`заменой` находят те же документы, что `замена`
  (target-кейсы true).
- **SC-3** Фразы: `"plan id"` не матчит `assessment_plan_id`; настоящая фраза
  находится.
- **SC-4** No-regression: golden-кейсы продукта (SC-1…SC-4 docsbase, hit@k)
  остаются true после S2–S5.
- **SC-5** Цитаты: ни один hit не указывает на чанк сверх cap (+overlap ≈10%);
  `lines` валидны. *(MODIFIED в design-фазе: исключение для одиночных абзацев
  убрано — предел гарантирует срез по границе токена, аварийный посимвольный
  только для безпробельных блобов; см. design, компонент §4.3.)*
  *(MODIFIED SQ15: атомарные fence/table — единственное исключение: блоки не
  дробятся ради целостности кода/таблиц и могут превышать cap+overlap;
  поведение зафиксировано pin-тестами SQ13; см. design §9.)*
- **SC-6** Rebuild: смена `tokenizer_version` приводит к пересборке; старый индекс
  не читается молча.
- **SC-7** Офлайн: SC-8 продукта зелёный; в дефолтной сборке нет сетевых крейтов.
- **SC-8** (P3) Мультиязычность: CJK-запрос находится биграммами; Arabic с harakat
  находится без harakat; `ёлка` находится запросом `елка`.

## 10. Assumptions & challenges

| # | Челлендж | Резолюция |
|---|---|---|
| 1 | S1: golden-корпус мал (8 доков) — nDCG не абсолютная метрика | Метрики directional + no-regression на golden-кейсах продукта (SC-1…SC-4 docsbase); fixture расширяется RU-доками; baseline — эталон, не «цель» |
| 2 | S4: стемминг ломает exact-матч идентификаторов и SC-1 | Стем-замена только standalone-слов, идентификаторы — точные мульти-токены; FR-10 (keyword-marker); SC-1 продукта — обязательный регресс-тест |
| 3 | S2: cap/сплит меняют чанки → снапшоты цитат изменятся | Явное исключение из no-regression: снапшоты цитат обновляются delta; hit@k по классам без выпадений (FR-3). Delta включает дрейф хвостовых позиций (не только координаты); критерий — per-case hit@k (SQ15) |
| 4 | S3: забытый bump версии → silent stale index | Версия-константа рядом с токенайзером + тест «смена версии триггерит rebuild» (SC-6) |
| 5 | G6/S6: «без новых крейтов» vs Unicode-фолдинг | Дефолт — ручной минимум (ё/width/case); крейт только через ADR (Open questions) |
| 6 | NFR-1: стемминг/биграммы растят индекс → latency | Замер до/после обязателен; бюджет p95 не хуже текущего |
| 7 | S1/S5: подгонка под малый golden-корпус | Выигрыш принимается только если держится на всех классах запросов (RU/EN/идентификаторы/фразы); иначе изменение отклоняется |

**Requirement acceptance bar (для ключевых FR):** owner — владелец продукта;
trigger — индексация/запрос; observable outcome — метрики/цитаты/тесты; failure mode —
регресс рангов/устаревший индекс/сетевой запрос; non-goal — hybrid, форк k1/b.

## 11. Out of scope

- S7/hybrid (embedding-провайдеры, RRF, reranker, сеть) — спек `hybrid-search`.
- `k1/b` (только форк tantivy — отклонено ADR-13-контекстом).
- Semantic/LLM-chunking, late chunking, contextual retrieval.
- Словари CJK/Thai (lindera/jieba), reranker-модели.
- Изменение публичных форм ответов MCP/CLI; новые пользовательские конфиг-ключи.
- macOS, PDF/DOCX/HTML.

## 12. Open questions

1. `unicode-normalization`: крейт vs ручной минимум фолдинга. **Default:** ручной
   минимум; крейт — только через ADR при необходимости полного NFKC.
2. Точный состав target-кейсов S1 (RU/CJK/Arabic). **Default:** список из
   догфудинга + заготовки CJK/Arabic, уточняется в S1.
3. Порог «улучшения» на target-кейсах. **Default:** false→true на целевом кейсе
   без выпадений из top-k на остальных (hit@k, FR-3).
4. Значение cap (эквивалент токенов). **Default:** ≈300–500 токенов, уточняется
   замером в S2.
