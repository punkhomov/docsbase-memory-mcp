Ниже — техническое задание на первую версию **локальной Web-панели docsbase**. Его можно использовать как основу feature issue и плана реализации.

Архитектурные решения соответствуют нашему обсуждению. Названия новых модулей, настроек и HTTP-маршрутов предлагаемые: перед реализацией нужно сверить их с актуальным `main`. Среда недоступна, поэтому такую сверку я сейчас выполнить не могу.

**1. Цель и границы первой версии**

Добавить в стандартную поставку docsbase локальный интерфейс, через который пользователь сможет:

- увидеть зарегистрированные проекты и состояние выбранного проекта;
- выполнить поиск и изучить результаты;
- посмотреть действующую конфигурацию без раскрытия секретов;
- понять, доступен ли демон и какие возможности он поддерживает.

Панель должна работать без Node.js на компьютере пользователя, без CDN и без подключения к интернету для загрузки интерфейса.

В первую версию не входят:

- удалённый или многопользовательский доступ;
- редактирование конфигурации;
- управление моделями и загрузками;
- запуск переиндексации из интерфейса;
- полноценный просмотр файловой системы;
- официальный SDK для сторонних сайтов.

При этом поиск может обращаться к настроенному внешнему провайдеру, как и существующий CLI. Автономность интерфейса не означает запрет сетевых запросов уже выбранного поискового режима.

**2. Архитектура процессов и ответственность**

```mermaid
flowchart LR
    B["Браузер: Svelte SPA"]
    W["docsbase web: HTTP + встроенные ресурсы"]
    D["docsbase daemon"]
    S["Индексы, конфигурация, модели"]

    B <-->|"HTTP / JSON"| W
    W <-->|"Асинхронный локальный IPC"| D
    D <--> S
```

`docsbase web` — отдельный процесс, запускаемый из того же исполняемого файла, что и остальные команды CLI.

| Компонент | Ответственность |
|---|---|
| Браузер | Навигация, формы, отображение результатов, состояния загрузки и ошибок |
| Web-процесс | HTTP, защита локального API, раздача ресурсов, проверка формы запросов, адаптация HTTP к IPC |
| Демон | Поиск, состояние проектов, разрешённая конфигурация, доступ к индексам и провайдерам |
| Общие контракты | Типы запросов и ответов, идентификаторы ошибок, согласование возможностей |

Web-процесс не открывает базу данных и индексы самостоятельно, не создаёт второй экземпляр поискового движка и не загружает модели.

Если для экрана не хватает данных в IPC, расширяется контракт демона. Получать эти данные обходным чтением его внутренних файлов из Web-процесса нельзя.

**3. Технический стек и структура**

Предлагаемый стек:

| Область | Решение |
|---|---|
| HTTP | Rust, Tokio, axum |
| Связь с демоном | Существующий асинхронный IPC-клиент |
| Frontend | Svelte, TypeScript, Vite |
| Стили | Scoped CSS, общие дизайн-токены |
| HTTP-клиент браузера | `fetch`, `AbortController` |
| Браузерные проверки | Playwright |
| Контрактные типы | Rust-типы с генерацией TypeScript |
| Поставка | Статические frontend-ресурсы внутри бинарника |

Новые Rust-зависимости должны соответствовать MSRV проекта, сейчас это Rust 1.88, и пройти предусмотренное репозиторием архитектурное обоснование. Конкретные версии выбираются после проверки совместимости.

Предлагаемая структура:

```text
src/web/
  mod.rs
  server.rs
  settings.rs
  assets.rs
  daemon_client.rs
  api/
    projects.rs
    status.rs
    search.rs
    configuration.rs

web/
  src/
    app/
    pages/
    features/
      projects/
      search/
      configuration/
    shared/
      api/
      ui/
      styles/
  tests/
```

Frontend организован по пользовательским возможностям. Каждая возможность содержит свою логику и компоненты. Страницы собирают их вместе.

Общее состояние приложения ограничивается выбранным проектом, навигацией и сессией. Результаты поиска и состояние формы принадлежат поисковому экрану.

Общие IPC-типы не должны зависеть от модуля Web. Специфичные для HTTP представления можно определить в Web-модуле.

**4. Запуск и завершение**

Предлагаемые команды:

```text
docsbase web
docsbase web --open
docsbase web --port 8080
```

Поведение:

1. Разрешить и проверить настройки.
2. Подготовить локальный HTTP-сервер.
3. Подключиться к демону, при необходимости запустить его штатным механизмом.
4. Проверить совместимость протокола и возможностей.
5. Сообщить адрес панели.
6. При `--open` открыть браузер после готовности HTTP-сервера.

По умолчанию сервер слушает только loopback. Порт `0` означает выбор свободного порта операционной системой.

Текущая директория используется для выбора начального проекта, если она соответствует зарегистрированному проекту. Открытие панели само по себе не регистрирует директории и не запускает индексацию.

Дополнительные требования:

- занятый явно указанный порт даёт понятную ошибку;
- невозможность открыть браузер не завершает работающий сервер: адрес остаётся доступен в терминале;
- потеря демона после запуска отображается в интерфейсе;
- закрытие вкладки не останавливает Web-процесс;
- `Ctrl+C` завершает Web-процесс и его запросы;
- завершение Web-процесса не останавливает общий демон.

При восстановлении соединения можно повторять безопасное чтение состояния. Уже отправленный поисковый запрос автоматически повторять нельзя: он мог начать платную работу у провайдера.

**5. IPC, конкурентность и отмена**

HTTP-обработчики используют асинхронный IPC. Блокирующие операции должны оставаться в предназначенном для них ограниченном исполнителе; перенос всего приложения на async не является частью этой задачи.

Нужен ограниченный пул IPC-соединений:

- общее число соединений ограничено;
- число ожидающих запросов ограничено;
- привязка соединения к проекту учитывается при повторном использовании;
- очередь и получение соединения учитывают общий дедлайн запроса;
- поиск не может занять всю ёмкость, необходимую для статуса и конфигурации;
- число вкладок и проектов не приводит к неограниченному росту пула.

Конкретную реализацию резервирования ёмкости нужно выбрать после проверки существующего IPC-клиента.

Дедлайн запроса не начинается заново при переходе HTTP → очередь → IPC → демон. Web-процесс сохраняет ограничения, установленные поисковой подсистемой.

При отмене поиска:

1. Браузер отменяет HTTP-запрос.
2. Web-процесс прекращает ожидание и передаёт отмену через поддерживаемый IPC-механизм.
3. Физическая работа, которую нельзя немедленно остановить, продолжает учитываться до фактического завершения.
4. Соединение с незавершённым ответом нельзя возвращать в пул как свободное.

Следует проверить, действительно ли выбранная реализация HTTP обнаруживает отключение клиента и запускает отмену. Одного `AbortController` во frontend для доказательства этого недостаточно.

При перегрузке возвращается типизированная ошибка занятости, а очередь не растёт без ограничения.

**6. HTTP-контракт**

Предлагаемая группа маршрутов:

| Маршрут | Назначение |
|---|---|
| `GET /api/v1/session` | Состояние Web-сессии, версия и доступные возможности |
| `GET /api/v1/projects` | Зарегистрированные проекты |
| `GET /api/v1/projects/{id}/status` | Состояние выбранного проекта |
| `POST /api/v1/projects/{id}/search` | Выполнение поиска |
| `GET /api/v1/projects/{id}/config` | Безопасное представление эффективной конфигурации |

Идентификатор проекта получается из списка зарегистрированных проектов. API не принимает произвольный путь как разрешение открыть директорию.

Поисковые параметры опираются на существующий контракт. Web-слой не вводит альтернативные значения по умолчанию, ранжирование или собственную интерпретацию фильтров.

Следует явно различать:

- **интерпретацию запроса** — Syntax / Literal;
- **способ поиска** — доступные в проекте лексический, гибридный и другие режимы.

Если демон не поддерживает Literal, интерфейс объясняет недоступность. Подмена Literal на Syntax недопустима.

Ошибки имеют стабильный машинный код, безопасное сообщение и идентификатор запроса. Должны различаться как минимум:

- неверный запрос;
- неизвестный проект;
- неподдерживаемая возможность;
- недоступность демона;
- занятость;
- истечение дедлайна;
- внутренняя ошибка.

В HTTP-ответах не должны появляться трассировки, ключи провайдеров или необработанные диагностические сообщения с секретами.

TypeScript-типы генерируются из Rust-контрактов. CI проверяет отсутствие расхождений. Для диагностики несовместимого ответа нужны также проверки во время выполнения: TypeScript сам по себе не проверяет полученный JSON.

**7. Конфигурация и значения по умолчанию**

Применяется уже согласованный принцип: компоненты получают полностью разрешённые типизированные настройки.

Web-компонент владеет собственными настройками и их дефолтами. Общая инфраструктура конфигурации вызывает контракт компонента, но не содержит отдельную копию знаний о нём.

Предлагаемые группы настроек:

| Группа | Примеры |
|---|---|
| HTTP | Loopback-адрес, порт, ограничения размера запроса |
| IPC | Размер пула, ограничение очереди, резерв для служебных запросов |
| Жизненный цикл | Бюджет запуска и корректного завершения |
| Обновление интерфейса | Интервал обновления состояния |
| Защитные ограничения | Максимально допустимые размеры ответов там, где это требуется |

Поисковые лимиты, бюджеты провайдеров и параметры индекса остаются у их текущих владельцев.

Frontend получает разрешённые настройки и возможности от сервера. Конструкция вида «если сервер не передал лимит, поставим известные только браузеру 100» запрещена.

Фиксированными могут оставаться:

- версия протокола и имена маршрутов;
- значения перечислений контракта;
- внутренние идентификаторы UI;
- дизайн-токены, размеры отступов, цвета;
- инварианты безопасности локального режима.

Для таких значений должно быть понятно, почему это часть протокола, оформления или инвариант, а не настраиваемая эксплуатационная политика.

Изменение Web-настроек в первой версии применяется при перезапуске Web-процесса. Оно не должно требовать инвалидации поискового индекса.

Полная реализация #78 не блокирует MVP, но новый Web-компонент должен следовать согласованной модели владения настройками.

**8. Безопасность локального доступа**

Loopback сам по себе не защищает API от запросов, инициированных посторонним сайтом в браузере.

Для первой версии требуется:

- привязка только к loopback;
- проверка допустимых `Host` и `Origin`;
- отсутствие разрешающего произвольные сайты CORS;
- локальная сессия для доступа к API;
- ограничения размера запросов;
- запрет выдачи произвольных локальных файлов;
- защита от исполнения HTML/JavaScript из документов и поисковой выдачи.

Предлагаемый вход в панель:

1. Web-процесс создаёт случайный одноразовый bootstrap-токен.
2. Адрес для открытия содержит его во фрагменте URL.
3. Frontend обменивает токен на `HttpOnly`, `SameSite=Strict` session cookie.
4. Фрагмент удаляется из адресной строки.
5. Bootstrap-токен перестаёт действовать.

Токен не должен попадать в HTTP query string, журналы запросов или `Referer`. Cookie должна быть привязана к конкретному запуску сервера и корректно проверяться даже при работе других localhost-приложений.

Это локальная сессия, без пользователей, паролей и ролей. Удалённый доступ потребует отдельного проекта.

Для ресурсов задаётся CSP, исключающая загрузку скриптов с внешних источников. Секретные ответы API не кэшируются. Service worker в MVP не нужен.

**9. Интерфейс и визуальное оформление**

Панель должна выглядеть как законченный инструмент для работы с документацией.

Общая компоновка:

- слева — навигация;
- сверху — выбранный проект и состояние соединения;
- основная область — текущий экран;
- на узком экране навигация сворачивается, содержимое остаётся доступным без горизонтального скролла всей страницы.

Визуальный стиль:

- спокойная нейтральная палитра;
- один основной акцентный цвет;
- ясная типографическая иерархия;
- моноширинное отображение путей, конфигурации и технических значений;
- достаточные отступы и аккуратные разделители;
- цвет состояния всегда сопровождается текстом или значком;
- без декоративных графиков с искусственными данными.

Обязательные состояния каждого экрана: загрузка, данные, отсутствие данных, ошибка, потеря соединения.

Недоступное значение показывается как «недоступно», а не как ноль. История и динамика отображаются только при наличии настоящих измерений.

**10. Экран проектов и состояния**

Пользователь должен видеть:

- список зарегистрированных проектов;
- имя и путь выбранного проекта;
- доступность демона;
- доступные поисковые возможности;
- количество документов и чанков, если демон предоставляет эти значения;
- состояние индексации и моделей в пределах существующего публичного контракта.

Выбор проекта меняет контекст поиска и конфигурации.

При смене проекта незавершённые запросы старого контекста отменяются. Поздний ответ от старого проекта не может заменить данные нового.

Обновление состояния:

- не создаёт перекрывающихся одинаковых запросов;
- сокращается или приостанавливается для скрытой вкладки;
- использует разрешённый сервером интервал;
- при ошибке сохраняет различие между последними известными и актуальными данными.

**11. Экран поиска**

Содержит:

- поле запроса;
- явную кнопку поиска;
- доступные режимы;
- основные фильтры существующего API;
- список результатов;
- просмотр фрагмента или выбранного результата;
- диагностические сведения, если backend их предоставляет.

Поиск запускается по отправке формы, а не на каждое нажатие клавиши. Это особенно важно при использовании платных провайдеров.

Для результата показываются доступные данные: заголовок, путь, фрагмент, релевантные метаданные. Численные оценки не выдаются за проценты уверенности.

Обязательное поведение:

- предыдущий запрос можно отменить;
- новый запрос не может быть перезаписан поздним ответом старого;
- пустая выдача отличается от ошибки;
- выбранный проект и параметры запроса очевидны;
- диагностические подробности не перегружают основную выдачу;
- запрос не повторяется автоматически после неопределённого исхода;
- содержимое документов отображается безопасно.

Для MVP достаточно безопасного текстового предпросмотра данных из поискового ответа. Полный документ можно показывать только при наличии подходящего IPC-контракта с ограничениями размера и проверкой принадлежности проекту.

Поисковые запросы и содержимое результатов по умолчанию не сохраняются в `localStorage` и не помещаются в URL.

**12. Экран конфигурации**

Показывает эффективную конфигурацию выбранного проекта, полученную от демона.

Настройки группируются по компонентам. Для значения показываются:

- название;
- действующее значение;
- краткое описание, если оно есть в схеме;
- источник значения, если backend действительно способен его определить.

Нельзя вычислять происхождение сравнением с дефолтом: явно заданное значение может совпадать с ним.

Секреты маскируются **до передачи браузеру**. Предпочтителен специальный безопасный DTO; сериализовать весь внутренний конфиг и затем удалять подозрительные поля ненадёжно.

Допустимо показать, что секрет настроен, без его значения. Скопировать конфигурацию можно только в безопасном представлении.

Редактирование и применение изменений отсутствуют. Будущий редактор должен использовать план изменений и инвалидации от владельцев компонентов; frontend не должен самостоятельно решать, когда перестраивать индекс.

**13. Сборка и поставка**

Web включается в стандартную пользовательскую сборку, релизы и установщики. В текущей модели проекта это означает включение в `cli-full`.

Внутренний Cargo feature `web` сохраняется, чтобы можно было явно собрать вариант без панели. Различие между стандартной поставкой и минимальной source-сборкой должно быть документировано.

Сборка frontend:

1. Установить зависимости по зафиксированному lockfile.
2. Проверить TypeScript и выполнить frontend-тесты.
3. Собрать production-ресурсы.
4. Встроить их в Rust-бинарник.
5. Проверить запуск собранного бинарника.

`build.rs` не скачивает npm-зависимости и не выполняет скрытую сетевую сборку. Отсутствие необходимых ресурсов при включённом `web` должно давать понятную ошибку с инструкцией.

Для опубликованного Cargo-пакета, если этот канал поставки поддерживается проектом, подготовленные ресурсы должны входить в пакет. Установка из него не должна требовать Node.js. Сборка из Git может требовать явно описанного frontend-шага.

После установки программа работает без Node.js, исходников frontend и каталога `node_modules`.

**Ограничение 40 МиБ снимается.** Необходимо согласованно обновить нормативные документы, проверки артефактов и инструкции. Новый произвольный предел не вводится.

CI продолжает измерять:

- размер исполняемого файла;
- размер встроенных frontend-ресурсов;
- размер дистрибутива.

Это изменение касается бюджета размера поставки. Остальные ограничения памяти, очередей и поисковой работы автоматически не отменяются.

**14. Тестирование**

| Уровень | Что проверяем |
|---|---|
| Rust unit | Настройки, валидация, отображение ошибок, безопасные DTO |
| Rust integration | HTTP → реальный IPC → демон, жизненный цикл, совместимость |
| Frontend | Существенная логика состояния, отмена, переключение проекта, ошибки |
| Playwright | Основные пользовательские сценарии на настоящем приложении |
| Проверка артефакта | Встроенные ресурсы и запуск без frontend-инструментов |

Обязательные интеграционные сценарии:

- запуск Web при работающем демоне;
- штатный запуск отсутствующего демона;
- демон недоступен или завершился во время работы;
- несовместимые возможности протокола;
- занятый порт;
- корректное завершение Web без остановки демона;
- отмена запроса и истечение дедлайна;
- насыщение поисковой ёмкости с сохранением доступа к статусу;
- отсутствие выдачи секретов;
- ограничение тела запроса;
- отказ запросам с недопустимым `Host`, `Origin` или сессией;
- отсутствие обхода путей при раздаче ресурсов.

Обязательные Playwright-сценарии:

- открытие панели и выбор проекта;
- успешный поиск с ожидаемым документом;
- Syntax / Literal при поддержке демоном;
- пустая выдача;
- ошибка запроса;
- отмена или замена поиска;
- переключение проекта при незавершённом запросе;
- безопасное отображение документа с HTML-подобным содержимым;
- просмотр замаскированной конфигурации;
- потеря связи с демоном;
- основные действия с клавиатуры;
- корректное отображение на узком экране.

Для основных E2E используются настоящие Web-процесс и демон с маленьким локальным набором документов. Ответы поиска не подменяются моками.

Сложные состояния провайдеров можно проверять управляемыми тестовыми провайдерами. Полная поставочная сборка сохраняет embedding-возможности, но браузерные тесты не требуют реального ключа или скачивания большой модели.

Фиксированные `sleep` запрещены как способ синхронизации. Тесты ждут наблюдаемую готовность, ответ, событие или изменение интерфейса. Ограничение времени служит защитой от зависания, а не утверждением, что CI обязан выполнить поиск за локальный бюджет.

Тесты логики таймеров используют управляемое время там, где это возможно. Браузерные проверки взаимодействия с отдельным демоном не считают подмену браузерных часов заменой серверного времени.

**15. CI**

Предпочтительная схема — расширить существующие задания, сохранив понятную структуру:

| Задание | На PR и main | Основные проверки |
|---|---|---|
| `docs` | Да | Документация, ссылки, согласованность описаний |
| `linux` | Да | Rust, frontend-проверки, production-сборка UI, Playwright Chromium |
| `macos` | Да | Rust и короткая проверка Web из собранного бинарника |
| `windows` | Да | Rust и короткая проверка Web из собранного бинарника |

Playwright использует уже подготовленный в Linux-задании бинарник, когда это совместимо с текущей организацией сборки. Дополнительная сборка допускается только при реальном различии профиля или требуемых возможностей.

Отдельная универсальная job «собрать Rust для всех ОС» не вводится: Linux-бинарник не заменяет native-сборки Windows и macOS.

Frontend можно собирать в каждом native-задании либо передавать одинаковый bundle артефактом. Окончательный выбор принимается после замера: дополнительная зависимость между jobs не должна добавляться только ради небольшой экономии.

При падении браузерного теста сохраняются:

- Playwright trace;
- screenshot;
- сообщения консоли браузера;
- безопасные журналы Web и демона;
- идентификаторы и параметры запуска тестовой среды.

Автоматические повторы тестов не должны скрывать нестабильность. Полный браузерный набор на всех ОС в MVP не требуется.

Дополнительные браузеры можно добавить в scheduled/manual-проверки, если появится соответствующая заявленная поддержка.

**16. Ручная проверка и наблюдаемость**

Помимо автоматических тестов требуется фактически открыть панель через Playwright/браузер и проверить:

- обычный и узкий экран;
- длинные пути, заголовки и фрагменты;
- большие значения конфигурации;
- загрузку, пустую выдачу и ошибки;
- фокус и управление клавиатурой;
- отсутствие ошибок консоли и неожиданных сетевых запросов;
- отсутствие зависания интерфейса при выполнении поиска.

Скриншоты основных экранов и состояний прикладываются к PR как свидетельство проверки. Автоматические screenshot-тесты для всех экранов не обязательны.

Журналы должны позволять связать HTTP-запрос с IPC-операцией. Допустимо записывать тип операции, длительность, итог и идентификатор запроса.

По умолчанию не логируются поисковые тексты, содержимое документов, токены сессий и секреты конфигурации.

**17. Последовательность реализации**

| Этап | Результат | Условие завершения |
|---|---|---|
| 1. Спецификация и аудит | Уточнённые контракты, зависимости, правила поставки и список недостающих IPC-операций | Нет неразрешённых вопросов, блокирующих каркас |
| 2. Backend и запуск | Команда Web, сессия, встроенные ресурсы, подключение к демону, настройки | Интеграционные тесты запуска, безопасности и завершения |
| 3. Интерфейс и поиск | Навигация, проекты, состояние, поиск и безопасная конфигурация | Основные сценарии проходят через настоящий IPC |
| 4. Поставка и приёмка | Default-включение Web, CI, документация, проверки артефакта и оформление | Native-проверки и Playwright зелёные, ручная проверка выполнена |

Этапы можно разбить на последовательные PR. Включение Web в стандартную поставку происходит после готовности пользовательского сценария и обязательных проверок.

Если по ходу работы обнаруживается существующий баг, он либо исправляется отдельным небольшим изменением, либо оформляется как issue с доказательствами и связью с блокируемым этапом.

**18. Итоговые критерии приёмки**

Фича готова, когда выполнены все следующие условия:

- стандартный установленный docsbase содержит команду `web`;
- `docsbase web --open` открывает работоспособную локальную панель;
- пользователь может выбрать проект, выполнить поиск и посмотреть безопасную эффективную конфигурацию;
- поиск использует существующий демон и сохраняет его семантику;
- Web не создаёт копии индекса, базы или модели;
- очереди и конкурентность ограничены;
- отмена и дедлайны проверены на границах HTTP и IPC;
- медленный поиск не блокирует получение состояния;
- интерфейс работает без внешних frontend-ресурсов;
- секреты не передаются браузеру;
- бинарник запускается без Node.js;
- ограничение 40 МиБ снято, измерение размера сохранено;
- проверки Linux/macOS/Windows и Playwright проходят;
- интерфейс реально просмотрен в браузере, включая ошибки и узкий экран;
- документация описывает запуск, конфигурацию, сборку, ограничения локального режима и диагностику.

Для начала реализации дополнительных продуктовых решений от тебя не требуется. Основная оставшаяся подготовка — сверка этого задания с текущим кодом и доступными IPC-контрактами после восстановления среды.

## Delta 2026-11-13 — W7: shutdown до готовности (#138)

- Обработчики завершения устанавливаются синхронно до публикации launch URL и
  запуска браузера. Ошибка регистрации не сопровождается объявлением готовности.
- Сохраняется существующий OS seam: SIGINT/SIGTERM на Unix, Ctrl+C/закрытие консоли
  на Windows. Сигнал, пришедший во время объявления/запуска браузера, сохраняется
  для завершения Web после возврата callback. Немедленная отмена блокирующего
  browser spawn этой задачей не обещается.
- Завершение frontend не останавливает общий демон; runtime shutdown остаётся
  ограничен действующим `shutdown_timeout_ms`.
- Проверка опасного интервала выполняется в свежем subprocess, без обработчиков
  от других тестов. Настоящий real-daemon lifecycle test сохраняется; при отказе
  он сообщает фактический статус завершения. Нет retries, skips, новых runtime
  таймаутов или ослабления существующих проверок. Новый subprocess-test ограничен
  десятью секундами для обнаружения зависания.
