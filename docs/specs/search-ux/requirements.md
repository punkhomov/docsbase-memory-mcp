# Search UX — Requirements (SPECIFICATION)

> Feature: `search-ux` — ответ поиска должен быть пригоден агенту с первого
> вызова: фрагмент текста, без пяти чанков одного файла, с фильтрами по пути и
> тегам. Всё — аддитивно и по умолчанию выключено.
> Контекст: `docs/specs/constitution.md`, `docs/specs/search-quality/`
> (форма выдачи, no-regression), `docs/specs/search-telemetry/` (`explain`,
> `score_scale`), `docs/specs/ann-index/` (FR-10 — заморозка формы `search_docs`),
> `docs/specs/search-benchmark/` (метрика `duplicate_path_ratio`).

## 1. Problem

Агент получает цитату `{chunk_id, path, heading_path, lines, score}` и, чтобы
понять, о чём чанк, обязан сделать второй вызов (`get_doc`/`read_neighbors`).
Два дефекта измерены нашим же корпусом:

1. **Фрагмента нет.** В ответе только координаты (`path`, `lines`). Это лишний
   round-trip на каждый хит и лишний расход контекста агента: он либо читает
   весь файл, либо не читает ничего и отвечает по заголовку.
2. **Один файл заполняет выдачу.** `duplicate_path_ratio` в baseline:
   `0.018` (identifier) … `0.582` (`ru_morph`), `0.487` (`multi_relevant`),
   `0.510` (`long_doc_boundary`). В половине срезов больше трети хитов — чанки
   одного и того же документа; агент видит не «пять источников», а «один файл
   пять раз».
3. **Нет фильтра по пути.** Агент, работающий в подкаталоге (`docs/`, `src/`,
   `specs/`), не может сузить поиск и получает хиты из чужих разделов. При этом
   `docs.rel_path` уже уникально проиндексирован (`UNIQUE(project_id, rel_path)`,
   `migrations.rs:31`), то есть фильтр по префиксу — это range scan, а не новая
   схема.
4. **Frontmatter — мёртвые данные.** `Frontmatter{title,tags}` парсится и
   пишется в `docs.frontmatter_json` (`repo.rs:112`), но не читается ни одним
   запросом: теги в документе не влияют ни на что.

## 2. Goals / Non-goals

**Goals**
- G1: каждый хит несёт короткий фрагмент текста, достаточный, чтобы решить
  «читать файл или нет».
- G2: выдача не заполняется чанками одного файла, когда есть другие источники.
- G3: поиск можно сузить по префиксу пути и по тегам frontmatter.
- G4: всё аддитивно и по умолчанию выключено: запрос без новых ключей даёт
  побайтово прежний ответ, `baseline.json` не перегенерируется.
- G5: ни новой схемы tantivy, ни переиндексации у пользователя — только SQL по
  существующим индексам и пост-фильтрация.

**Non-goals**
- MMR и любая диверсификация по векторам — сначала измеряем дедуп по пути
  (он ловит наблюдаемые 58% повторов); MMR требует векторов в момент ответа.
- Полнотекстовые фильтры по заголовкам/датам, фасетный поиск, DSL.
- Изменение ранжирования: дедуп по пути — пост-фильтр, он не меняет порядок
  оставшихся хитов.
- Подсветка (highlight) с разметкой — фрагмент отдаётся как текст.
- Кросс-проектный поиск (`scope` остаётся `project`).
- Кэш результатов и query-кэш — спек `search-cost`.

## 3. Users / Actors

- **Coding-агент** (основной): один вызов — один взгляд на источники.
- **CLI-пользователь**: `docsbase search --snippet --path docs/`.
- **Владелец**: следит, чтобы `duplicate_path_ratio` и recall не разъехались.

## 4. Prioritized user stories

### P1 — U1: Фрагмент в хите
**As** агент, **I want** видеть кусок текста чанка, **so that** не делать второй
вызов на каждый хит и не читать файл целиком.

- **Why P1:** прямой расход round-trip и контекста на каждом поиске.
- **Independent test:** `search_docs {snippet: true}` возвращает у каждого хита
  поле `snippet` — подстроку `chunks.text` этого чанка, ≤ 240 символов.
- **Acceptance scenarios:**
  - Given запрос с `snippet: true`, When ответ получен, Then каждый хит несёт
    `snippet`, который является подстрокой текста своего чанка (проверяется по
    БД, а не по форме).
  - Given фрагмент длиннее лимита, When он отдаётся, Then он обрезан по границе
    символа (не байта) и помечен `snippet_truncated: true`.
  - Given `snippet: false`/отсутствует, When ответ получен, Then поля `snippet`
    нет вовсе (не `null`).

### P1 — U2: Дедуп по документу
**As** агент, **I want** видеть разные файлы, **so that** пять хитов не оказываются
одним документом.

- **Why P1:** 58% повторов в `ru_morph` — измеренный дефект, а не гипотеза.
- **Independent test:** на срезе `ru_morph` запрос с `dedupe: "path"` даёт
  `duplicate_path_ratio ≤ 0.20` при неухудшившемся recall@10 по уникальным файлам.
- **Acceptance scenarios:**
  - Given `dedupe: "path"`, When 8 чанков одного файла попадают в топ, Then в
    выдаче остаётся не больше `n_per_doc` (по умолчанию 1) из них, а освободившиеся
    места занимают следующие кандидаты из того же окна.
  - Given `dedupe: "none"` (по умолчанию), When ответ получен, Then порядок и
    состав идентичны текущим.
  - Given один файл — единственный релевантный, When `dedupe: "path"`, Then
    выдача не пустеет: `n_per_doc` можно поднять, и недостача не превращается в
    пустой ответ.

### P1 — U3: Фильтр по пути и тегам
**As** агент в подкаталоге, **I want** сузить поиск, **so that** не получать хиты
из чужих разделов.

- **Why P1:** при 20k документов половина выдачи — не тот раздел.
- **Independent test:** 50 запросов с `path_prefix: "docs/"` дают ноль хитов вне
  префикса; `tags: ["api"]` даёт только документы, у которых тег есть во
  frontmatter.
- **Acceptance scenarios:**
  - Given `path_prefix: "docs/"`, When ответ получен, Then каждый `path`
    начинается с префикса; фильтр применяется до добора кандидатов, чтобы выдача
    не оказалась короче `limit` при достаточном числе совпадений.
  - Given `tags: ["api"]`, When ответ получен, Then каждый документ содержит этот
    тег в `frontmatter_json`; документы без frontmatter не проходят.
  - Given префикс, который ничего не матчит, When ответ получен, Then `hits` пуст,
    а при `explain: true` — `meta.degraded` содержит `filter-empty` (не ошибка).

## 5. Functional requirements

- **FR-1** (must) `search_docs` принимает `snippet: bool` (по умолчанию `false`).
  При `true` каждый хит получает `snippet` (≤ `SNIPPET_MAX_CHARS = 240`) и, если
  текст обрезан, `snippet_truncated: true`. Фрагмент — подстрока `chunks.text`
  этого `(doc_id, seq)`, взрезанная по границе символа (не байта).
- **FR-2** (must) `dedupe: "none"|"path"` (по умолчанию `"none"`) и
  `n_per_doc: usize` (по умолчанию `1`, `1..=10`, только вместе с
  `dedupe: "path"`; при `dedupe: "none"` — протокольная ошибка). Дедуп —
  пост-фильтр после ранжирования: порядок оставшихся хитов не меняется, а
  недостача добирается следующими кандидатами из того же окна `fetch`.
- **FR-3** (must) `path_prefix: string` — префикс project-relative пути, применяется
  к кандидатам **до** ранжирования; пустой/отсутствующий — без фильтра.
  Префикс не нормализуется молча: `docs/` и `docs` — разные префиксы (второй
  матчит `docsx.md`), это документируется.
- **FR-4** (must) `tags: [string]` — AND по всем тегам; источник —
  `docs.frontmatter_json`. Отсутствие `frontmatter_json` у документа = нет тегов.
- **FR-5** (must) Пустой результат из-за фильтра — не ошибка: `hits: []`, а при
  `explain: true` в `meta.degraded` добавляется токен `filter-empty`. Набор токенов
  расширяется по правилу `search-telemetry` FR-4 (только добавление).
- **FR-6** (must) Дефолтный ответ не меняется: без новых ключей `hits[]` побайтово
  прежний. Гейт `metrics_match_baseline` зелёный **без** перегенерации
  `baseline.json`. Все новые поля — opt-in.
- **FR-7** (must) Датированные дельты: `ann-index` FR-10 («форма `search_docs` не
  меняется») и `search-quality` §2/§11 («фильтры/сниппеты/дедуп вне области»)
  получают запись о том, что аддитивные opt-in поля разрешены этим спеком.
- **FR-8** (must) `docs/MCP.md` и `CHANGELOG` описывают новые ключи и поля в том
  же изменении.

## 6. Non-functional requirements

- **NFR-1 Performance.** `snippet: true` добавляет ≤ 1 SQL-запрос на хит того же
  соединения (`chunk_text` уже используется реранком) и ≤ 1 мс p95 на 10 хитов;
  `dedupe: "path"` и `path_prefix` не добавляют запросов на хит.
- **NFR-2 No new crates.** Обрезка по символам — `char_indices`, без
  `unicode-segmentation`; дефолтная сборка остаётся офлайн.
- **NFR-3 No reindex.** Ни одна часть не требует новой схемы tantivy или
  переиндексации; `docs.rel_path` уникально проиндексирован, `frontmatter_json`
  уже пишется.
- **NFR-4 Portability.** Linux/Windows/macOS зелёные; тесты с `\r\n` в тексте
  чанка (обрезка не должна рвать пару).
- **NFR-5 Security/Privacy.** Фрагмент не выходит за пределы текста чанка; ничего
  не логируется.
- **NFR-6 Evidence.** Дедуп и фильтры принимаются только с замером на
  `search_bench` (recall@10 по уникальным файлам + `duplicate_path_ratio`), не по
  ощущению.

## 7. Data model

- Никаких изменений схемы БД.
- `snippet` — derived из `chunks.text` (`repo::chunk_text`).
- `tags` — читаются из `docs.frontmatter_json` (JSON-массив `tags`); парсинг
  терпим к отсутствию/мусору (нет тегов, не ошибка).
- `filter-empty` — новый токен `meta.degraded` (extension по `search-telemetry`).

## 8. Interfaces

- MCP `search_docs {query, limit?, scope?, rerank?, explain?, snippet?, dedupe?,
  n_per_doc?, path_prefix?, tags?}`; `hits[]` получает `snippet`/
  `snippet_truncated` только при `snippet: true`.
- CLI `docsbase search --snippet --dedupe path --n-per-doc N --path PREFIX --tag T`
  (флаги повторяемы для `--tag`).
- Тестовые: `--test hybrid_ranking` (дедуп/сниппет на четырёх конфигурациях),
  `--test search_bench` (замер `duplicate_path_ratio`/recall), `--test mcp_docs`
  (схема и границы).
- `PROTOCOL_VERSION` не меняется.

## 9. Measurable success criteria

- **SC-1** Дефолт: без новых ключей `hits[]` побайтово прежний; baseline не
  перегенерирован; гейт зелёный.
- **SC-2** Фрагмент: каждый хит с `snippet: true` несёт подстроку своего чанка;
  длина ≤ 240 символов; `snippet_truncated` корректен; без `snippet` поля нет.
- **SC-3** Дедуп: на `ru_morph` `duplicate_path_ratio ≤ 0.20` при recall@10 по
  уникальным файлам не ниже текущего.
- **SC-4** Фильтры: `path_prefix` не пропускает чужое; `tags` — AND; пустой
  результат даёт `filter-empty`, а не ошибку.
- **SC-5** Границы: `n_per_doc` без `dedupe` — протокольная ошибка; `tags: []` —
  без фильтра; мусор в `frontmatter_json` не роняет поиск.
- **SC-6** Офлайн/зависимости: дерево-гейт зелёный, новых крейтов нет.

## 10. Assumptions & challenges

| # | Челлендж | Резолюция |
|---|---|---|
| 1 | Дедуп может уронить recall на запросах, где один файл — единственный ответ | `n_per_doc` ≥ 1 и добор из окна; SC-3 требует неухудшения recall по уникальным файлам; дефолт — `"none"` |
| 2 | Фильтр до ранжирования может обеднить выдачу | Фильтр применяется к кандидатам окна (`fetch`) и добирается в пределах окна; иначе — `filter-empty`, а не тихое усечение |
| 3 | `tags` из frontmatter — свободный текст, мусор в JSON | Парсинг терпимый: не массив/не строки → нет тегов; тест на мусор |
| 4 | Обрезка по байтам рвёт UTF-8 | `char_indices`, тест с кириллицей и эмодзи |
| 5 | `path_prefix` без нормализации удивляет (`docs` матчит `docsx.md`) | Задокументировано явно; нормализация — только если появятся жалобы |
| 6 | Дельты в двух спеках забыты → формальный конфликт | FR-7: датированные записи в `ann-index` и `search-quality` в этом же PR |

## 11. Out of scope

- MMR, семантическая диверсификация, rerank-по-новизне.
- Фильтры по дате/заголовку/языку, фасеты, DSL.
- Подсветка с разметкой (только текст фрагмента).
- Кэш результатов, query-кэш, стоимость (`search-cost`).
- Кросс-проектный `scope`.

## 12. Open questions

1. Лимит фрагмента: 240 символов против ~1 строка. **Default:** 240, константа,
   калибруется по `search_bench` без перегенерации baseline.
2. `snippet` всегда или только при `snippet: true`. **Default:** только при
   `true` — иначе SC-1 невозможен.
3. Дефолт `n_per_doc` при `dedupe: "path"`. **Default:** 1 (максимум разнообразия),
   `2` — по замеру.
4. Нужен ли `path_prefix` как «директория, а не строка» (добавлять `/`).
   **Default:** нет, префикс буквальный; см. челлендж 5.
