# Search Telemetry — Requirements (SPECIFICATION)

> Feature: `search-telemetry` — то, что вызывающий обязан узнать о своём же
> поиске: на какой шкале `score`, куда ушло время, в каком состоянии индекс и
> сколько стоил запрос.
> Контекст продукта: `docs/specs/docsbase-memory-mcp/{requirements,design}.md`,
> принципы: `docs/specs/constitution.md`, предшественники:
> `docs/specs/search-quality/` (форма выдачи), `docs/specs/ann-index/`
> (FR-9 «should» — диагностика ANN в `status`, не реализован),
> `docs/specs/hybrid-providers/` (стадии RRF/rerank).

## 1. Problem

MCP-поверхность отдаёт агенту `{chunk_id, path, heading_path, lines, score}`, и по
этому ответу невозможно понять, что именно произошло:

1. **Шкала `score` не названа.** Один и тот же ключ несёт сырой BM25 (неограничен,
   зависит от корпуса), RRF-фьюжн (`1/(k+rank)`, порядок 0.01–0.03) и выход
   reranker'а (`0..1`). Агент не может ни поставить порог, ни сравнить два ответа
   после смены конфигурации — а именно это он и делает, когда «поиск стал хуже».
2. **Время не атрибутировано.** `search_docs` не говорит, сколько заняли BM25,
   dense, RRF и rerank. Медленный поиск невозможно ни объяснить, ни починить, ни
   уложить в бюджет (`docs/specs/search-benchmark/` меряет только офлайн-прогон).
3. **Деградация невидима.** ANN может не обслуживать запрос (билд в процессе,
   граф неполный, `TooLarge`, ошибка загрузки) — читатель молча уходит в exact
   `stream_hashes`. Пользователь на 40k-файловом репозитории получает поиск в
   разы медленнее и не узнаёт об этом ни из ответа, ни из `status`: FR-9 спека
   `ann-index` объявлен как «should» и **не реализован** (`src/cli/status.rs` не
   содержит ни `ann`, ни `index_generation`).
4. **Стоимость невидима.** `estimate_cost_usd`/`cost_cap_from_env` живут только в
   тестах бенчмарка; в проде ни один ответ не говорит, сколько стоил вызов
   провайдера. Это блокирует любой разговор о бюджете (#5 в анализе состояния).
5. **Устаревание невидимо.** `index_generation` есть в БД и в dense-кэше, но не
   попадает ни в `status`, ни в ответ поиска: агент не может отличить «документ
   действительно изменился» от «индекс отстал на одну синхронизацию».

Документация уже приведена в соответствие (`docs/MCP.md`: раздел Scores), но
документ не заменяет поле в ответе.

## 2. Goals / Non-goals

**Goals**
- G1: по ответу поиска видно, на какой шкале `score` и какие стадии работали.
- G2: время разложено по стадиям, сумма сходится с общим.
- G3: `status` показывает `index_generation` и состояние ANN-тира (FR-9
  `ann-index`), включая причину отката в exact.
- G4: ответ несёт оценку стоимости запроса, когда её вообще можно посчитать
  (удалённый провайдер с usage), и `null`, когда нет.
- G5: всё это — без новых крейтов, без сети в дефолтной сборке и без влияния на
  ранжирование (гейт `metrics_match_baseline` остаётся зелёным без перегенерации).

**Non-goals**
- OpenTelemetry-экспорт, трейсы, коллектор, метрик-эндпоинт — отдельная итерация
  (потребует ADR и сетевого стека; см. `## 10`).
- Изменение ранжирования: окно rerank, `rrf_k`, веса, адаптивные пороги — спек
  `search-cost`.
- Сниппеты, дедуп по пути, фильтры — спек `search-ux`.
- Логи как второй канал наблюдаемости (агент их не читает).
- Стоимость как биллинг: оценка по прайс-таблице, не сверка со счётом провайдера.

## 3. Users / Actors

- **Coding-агент** (основной): читает JSON-ответ; должен решать, доверять ли
  порядку и стоит ли повторять запрос.
- **CLI-пользователь**: `docsbase search`, `docsbase status` — те же поля в JSON.
- **Владелец/мейнтейнер**: по `stage_ms` и `cost_usd` принимает решения о бюджете
  и видит, обслуживает ли ANN реальный трафик.

## 4. Prioritized user stories

### P1 — T1: Шкала и состав стадий
**As** агент, **I want** знать, что означает `score` в этом ответе, **so that**
я не сравниваю RRF-величины 0.016 с BM25-скором 12.4 и не строю на этом порог.

- **Why P1:** без этого ответ неинтерпретируем, а любая эвристика агента строится
  на сравнении чисел между вызовами.
- **Independent test:** для каждой из четырёх конфигураций (`Bm25`,
  `Bm25Rerank`, `Rrf`, `RrfRerank`) тест утверждает `meta.score_scale`.
- **Acceptance scenarios:**
  - Given проект с `ranking = "rrf"` и без reranker, When `search_docs`, Then
    `meta.score_scale == "rrf"`, `meta.stages == ["bm25","dense","rrf"]`.
  - Given проект с активным reranker, When `search_docs`, Then
    `meta.score_scale == "rerank"` и `"rerank"` присутствует в `meta.stages`.
  - Given лексический проект, When `search_docs`, Then
    `meta.score_scale == "bm25"`, `meta.stages == ["bm25"]`.

### P1 — T2: Тайминги по стадиям
**As** владелец, **I want** видеть, куда ушло время запроса, **so that** я могу
отличить медленный BM25 от медленного провайдера и обосновать бюджет.

- **Why P1:** это единственный источник данных для `search-cost` и для
  разбора «поиск стал медленнее».
- **Independent test:** тест с поддельным провайдером, который спит известное
  время, утверждает, что `stage_ms.rerank` не меньше этой задержки и что
  `bm25 + dense + rrf + rerank ≤ total × 1.1`.
- **Acceptance scenarios:**
  - Given любой поиск, When ответ получен, Then `meta.stage_ms` содержит запись
    для каждой активной стадии и `total`.
  - Given стадия не активна, When ответ получен, Then её ключа в `stage_ms` нет
    (а не `0`, который неотличим от «быстро»).
  - Given провайдер отвечает за T мс, When поиск, Then `rerank`/`dense` в
    `stage_ms` отражают T в пределах допуска.

### P1 — T3: Состояние индекса и ANN в `status`
**As** владелец, **I want** видеть в `status`, какой тир обслуживает поиск и
почему, **so that** молчаливый откат в exact перестаёт быть невидимым.

- **Why P1:** FR-9 `ann-index` объявлен и не реализован; сейчас единственный
  сигнал — `eprintln!` в лог демона, который агент не читает.
- **Independent test:** тест поднимает проект, где ANN обслуживает поиск, и
  проект, где он не может (граф неполный), и утверждает разные `ann.state` с
  непустым `reason` во втором случае.
- **Acceptance scenarios:**
  - Given проект, где ANN обслужил последний поиск, When `status`, Then
    `projects[i].ann.state == "ready"` и `ann.vectors > 0`.
  - Given ANN откатился в exact, When `status`, Then `ann.state` —
    `"building"`/`"too_large"`/`"fallback"` и `ann.reason` объясняет почему.
  - Given любой проект, When `status`, Then `projects[i].index_generation` равно
    `repo::index_generation` (не константа, не `null`).

### P2 — T4: Стоимость запроса
**As** владелец, **I want** видеть оценку стоимости каждого поиска, **so that**
бюджет обсуждается по числам, а не по ощущениям.

- **Why P2:** ценно, но зависит от T1/T2 (нужны стадии, чтобы знать, что
  считать) и от появления usage в провайдере.
- **Independent test:** поддельный транспорт с известным `usage` даёт непустой
  `meta.cost_usd`; локальный провайдер — `null`.
- **Acceptance scenarios:**
  - Given локальный провайдер (fastembed), When поиск, Then `meta.cost_usd` —
    `null` (локально стоимость не определена, а не «0.0»).
  - Given удалённый провайдер, вернувший usage, When поиск, Then
    `meta.cost_usd` — число по прайс-таблице провайдера.
  - Given провайдер не вернул usage, When поиск, Then `meta.cost_usd` — `null`
    (не выдуманная оценка).

## 5. Functional requirements

- **FR-1** (must) Ответ поиска несёт `meta`: `score_scale`
  (`"bm25"|"rrf"|"rerank"`), `stages` (активные, в порядке исполнения),
  `stage_ms` (по активным стадиям + `total`), `window` (фактический fetch после
  clamp), `index_generation`, `degraded` (массив причин, пустой если нет).
- **FR-2** (must) Форма ответа становится конвертом `{hits, meta}` вместо
  голого массива. Это осознанное ломающее изменение публичной формы (альфа:
  `README` уже заявляет ломающие изменения до `0.1.0`); фиксируется в
  `CHANGELOG` и `docs/MCP.md` в том же изменении. Сам элемент `hits[]` не
  меняется.
- **FR-3** (must) `stage_ms` содержит только реально исполненные стадии; сумма
  стадий не превышает `total` более чем на 10% (накладные расходы на замер).
- **FR-4** (must) `degraded` перечисляет причины отката, а не свободный текст:
  стабильные токены `"ann-building"`, `"ann-insufficient"`, `"ann-error"`,
  `"exact-fallback"`, `"no-rerank-stage"`. Пустой массив — нормальный ответ.
- **FR-5** (must) `status` (MCP и CLI) отдаёт `projects[i].index_generation` и
  `projects[i].ann` = `{state, vectors, estimated_bytes, reason}`; `state` —
  `disabled|loading|building|ready|too_large|fallback|stale`; `reason` непуст для
  любого состояния, кроме `ready`.
- **FR-6** (must) `meta.cost_usd` — число, когда провайдер вернул usage и цена
  известна; иначе `null`. Локальный провайдер всегда `null`. Прайс-таблица
  переезжает из тестового хелпера в прод-модуль без изменения значений.
- **FR-7** (must) `docsbase search` печатает тот же конверт `{hits, meta}`, что и
  MCP (одна форма, один код).
- **FR-8** (must) Замеры не влияют на ранжирование: при одинаковых входах
  `hits[]` побайтово совпадает с текущим ответом, гейт `metrics_match_baseline`
  зелёный **без** перегенерации `baseline.json`.
- **FR-9** (should) Имена полей совместимы с OTel GenAI conventions
  (`gen_ai.operation.name = retrieval`), чтобы будущий экспортёр лёг без
  переименований. Реализация экспортёра — вне спека.
- **FR-10** (should) `meta` помещается в ответ без заметного роста: конверт
  добавляет ≤ 300 байт на ответ при пустом `degraded`.

## 6. Non-functional requirements

- **NFR-1 Performance.** Накладные расходы телеметрии ≤ 1 мс p95 на поиск
  (замер до/после на `search_bench`); бюджет p95 поиска не меняется.
- **NFR-2 No new crates.** Дефолтная сборка остаётся офлайн; сетевых крейтов не
  добавляется; дерево-гейт (NFR-1 продукта) не трогается.
- **NFR-3 Maintainability.** Каждый FR покрыт автотестом; имена стадий и
  токены `degraded` — константы, а не строки по месту.
- **NFR-4 Portability.** Linux x86_64, Windows x64, macOS aarch64 — CI зелёный;
  тайминги в тестах с допусками (host-relative, как в `search_bench`).
- **NFR-5 Security/Privacy.** В `meta` нет содержимого документов и запроса;
  `cost_usd` не требует логирования промптов.
- **NFR-6 Evidence.** Ломающее изменение формы ответа фиксируется в `CHANGELOG`,
  `docs/MCP.md` и в спеке; никаких «молчаливых» изменений контракта.

## 7. Data model

- **`SearchMeta`** (сериализуемая структура, прод-код):
  `{score_scale: enum, stages: [enum], stage_ms: {<stage>: u64, total: u64},
  window: usize, index_generation: i64, degraded: [enum], cost_usd: Option<f64>}`.
- **`AnnState`** (прод-код, для `status`): `{state: enum, vectors: usize,
  estimated_bytes: u64, reason: Option<String>}` — источник: `DenseCache` +
  `AnnStore`, не повторный расчёт на каждый `status`.
- **`index_generation`** уже есть в `projects`/dense-кэше; выносится в JSON без
  изменения схемы БД.
- **Прайс-таблица** `estimate_cost_usd` переезжает из `tests/support/bench.rs` в
  `src/hybrid/` (значения и тесты сохраняются).

## 8. Interfaces

- MCP `search_docs {query, limit?, scope?, rerank?}` → **`{hits: [...], meta:
  {...}}`** (было: массив). Элемент `hits[]` не меняется.
- MCP `status` → добавляются `projects[i].index_generation` и
  `projects[i].ann`; остальные поля не меняются.
- CLI `docsbase search` → тот же конверт; `docsbase status` → те же новые поля.
- Тестовые: `cargo test --test hybrid_ranking` (шкала/стадии),
  `cargo test --test mcp_frontend` (форма конверта), `--test status` (ann/generation),
  `--test search_bench` (baseline без перегенерации).
- Конфиг: новых пользовательских ключей нет.

## 9. Measurable success criteria

- **SC-1** Шкала: для всех четырёх конфигураций `meta.score_scale` верен, и
  `meta.stages` совпадает с фактически исполненными стадиями.
- **SC-2** Тайминги: `bm25 + dense + rrf + rerank ≤ total × 1.1`; поддельный
  провайдер с задержкой T виден в соответствующей стадии.
- **SC-3** Статус: `projects[i].index_generation` равен значению из
  `repo::index_generation`; `ann.state` различает `ready` и откат, `reason`
  непуст при откате.
- **SC-4** Стоимость: локальный провайдер → `null`; удалённый с usage → число;
  удалённый без usage → `null`.
- **SC-5** Совместимость ранжирования: `hits[]` побайтово равен текущему ответу;
  `metrics_match_baseline` зелёный без перегенерации `baseline.json`.
- **SC-6** Офлайн и зависимости: дерево-гейт зелёный, новых крейтов нет,
  `cargo test --locked` в дефолтной сборке проходит.
- **SC-7** Документация: `docs/MCP.md` описывает конверт, `meta` и новые поля
  `status`; `CHANGELOG` фиксирует ломающее изменение формы.

## 10. Assumptions & challenges

| # | Челлендж | Резолюция |
|---|---|---|
| 1 | Конверт ломает форму ответа — все существующие клиенты и тесты | Альфа: ломающие изменения разрешены до `0.1.0`; одна форма вместо двух (без `explain`-флага и legacy-режима); `CHANGELOG` + `docs/MCP.md` в том же изменении; `hits[]` не меняется |
| 2 | Замер времени искажает сам себя | Замеры через `Instant` вокруг стадий; допуск 10% на сумму; NFR-1 — ≤1 мс p95 |
| 3 | `cost_usd` может быть выдумкой | Только по usage провайдера и прайс-таблице; локально — `null`, не `0.0`; отсутствие usage — `null` |
| 4 | `status.ann` требует состояния из `DenseCache`, который живёт в демоне | Читается из уже существующего состояния кэша, без нового билда; при отсутствии записи — `state: "disabled"` |
| 5 | OTel-имена без OTel-зависимости | Имена — константы, маппинг документируется; экспортёр — отдельный спек/ADR |
| 6 | Телеметрия может «протечь» в baseline | FR-8/SC-5: `hits[]` побайтово стабилен, гейт без перегенерации — обязательный регресс-тест |

## 11. Out of scope

- OTel/tracing-крейты, коллектор, дашборды, метрик-эндпоинт.
- Изменение окна rerank/весов/`rrf_k` и любые изменения ранжирования (`search-cost`).
- Сниппеты, дедуп, фильтры (`search-ux`).
- Хранение истории метрик, агрегаты по времени, перцентили в `status`.
- Логи как канал наблюдаемости.

## 12. Open questions

1. Конверт `{hits, meta}` против opt-in `explain: true`. **Default:** конверт
   (одна форма, один код-путь, альфа допускает ломающее изменение).
2. Гранулярность `stage_ms`: только стадии верхнего уровня или ещё подшаги
   (BM25 fetch vs top-k, dense embed vs ANN search). **Default:** верхний уровень;
   подшаги — по запросу при разборе конкретной деградации.
3. Источник `cost_usd`: usage из ответа провайдера или локальная оценка по
   токенам. **Default:** usage; без него — `null`.
4. Нужен ли `meta.trace_id` для корреляции с логом демона. **Default:** нет,
   пока нет экспортёра; `index_generation` + время покрывают разбор.
