# CI: что где гоняется и почему именно так

Дата: 2026-10-29. Обновлять вместе с `.github/workflows/ci.yml` — таблица ниже
обязана совпадать с джобами.

Документ отвечает на три вопроса, которые возникают каждый раз при виде
матрицы джобов: почему нельзя собрать один артефакт «со всеми фичами» и
раздать его всем, почему не 2<sup>n</sup> × ОС чеков, и почему у каждой джобы
свой кэш вместо одного общего.

## Лейны

| Джоба | Что делает | Что именно доказывает |
|---|---|---|
| `docs` | гигиена репозитория, версия в `CHANGELOG` | релизные артефакты и доки на месте |
| `linux` | `fmt`, `clippy` (default), `cargo test` (default) | **дефолтная сборка — это продукт** (`cargo install` = 0 фич): она компилируется, проходит линты и все тесты |
| `linux-hybrid` | `clippy --features hybrid-remote`, тесты фиче-зависимых таргетов, гейт NFR-1 (`cargo tree`) | крейт компилируется/линкуется **без** `hybrid-local`; в дефолтное дерево не протёк ни один сетевой/ML-крейт |
| `linux-local` | `clippy` (`hybrid-local`), powerset-матрица фич, фиче-зависимые тесты, **combo-сьюта** (`hybrid-local,hybrid-remote`), combo-clippy | главный рантайм-лейн всех провайдерских фич + «компилируется при любой комбинации фич» |
| `macos` | `fmt`, `clippy`, `check --features hybrid-local`, `test --features hybrid-local --lib`, `cargo test` (default) | платформенная семантика macOS + исполнение платформенного фичевого кода |
| `windows` | то же, что `macos`, для MSVC | то же для Windows |
| `nightly` | `--release` сьюта, `perf_budget`, `offline`, `platform_boundary` | то, что слишком дорого гонять на каждый PR (release panic strategy, RSS-бюджеты) |

## Две оси, а не одна матрица

Классы дефектов разные, поэтому и оси разные:

- **Ось фич** ловит: код, который компилируется только при точном наборе
  включённых фич; забытый `cfg`/импорт; warning-дрейф в выключенных ветках;
  `dep:` не в той фиче. Всё это — уровень компиляции/линта, платформа тут не
  при чём.
- **Ось ОС** ловит: FFI-типы и методы (`OsStrExt::encode_wide`, `&raw mut` в
  Win32-вызовах), `cfg(unix)`/`cfg(windows)` ветки, `rename` поверх
  существующего файла (на Windows падает, если цель открыта), удаление открытых
  файлов, sticky-права и `secure_dir`, named pipes vs unix-сокеты
  (`accept()` на BSD/macOS наследует `O_NONBLOCK`), зомби-процессы на macOS
  (`proc_pidinfo` + `SZOMB`), backends вотчера (`ReadDirectoryChangesW` /
  FSEvents / inotify).

Поэтому фичевая ось гоняется **один раз, на Linux**, компилятором:

```sh
cargo hack check --locked --feature-powerset --depth 2 --all-targets
```

`--depth 2` = все наборы из одной и двух фич (сейчас: `{}`,
`{remote}`, `{local}`, `{remote, local}`), то есть ровно тот случай
«работает только когда включены две», который не поймать одной
all-features сборкой. Появится третья фича — `--depth 2` автоматически
добавит все пары; полный powerset (2³ = 8 наборов) включается снятием
`--depth`.

Перемножать оси не нужно: баг уровня `cfg` проявится одинаково на всех трёх
ОС, а баг уровня платформы всё равно требует прогона *на* этой ОС, где
фичевый набор уже проверяется `check`/`clippy`/`--lib`-сьютой.

### Почему не «собрать всё со всеми фичами и раздать артефакт»

1. **All-features бинарь не «умеет всё»** — в нём отсутствует код выключенных
   веток. В `src/` есть `cfg(not(feature = ...))` сайты (admission'ы
   «пересобери с `--features hybrid-local`», remote-less режим) — all-features
   сборка их не компилирует и не тестирует.
2. **Дефолтная сборка — продукт.** Гейт NFR-1 (в дереве нет `fastembed`,
   `ort`, `tokenizers`, `hf-hub`, `ureq`, `reqwest`) про
   all-features сборку не говорит ничего.
3. **Линты feature-off не срабатывают.** Реальные падения этого класса уже
   были: `-D dead-code` на macOS ровно потому, что `hybrid-local` выключен;
   такой дефект all-features лейн не увидит никогда.
4. **Экономии нет.** All-features — самая тяжёлая сборка (~1.2 ГБ `target`).
   Тест-бинари всё равно свои на каждый набор фич, а дорогая часть — не
   компиляция зависимостей, а линковка ~35 тест-таргетов.

### Почему combo-сьюта — главный фичевый рантайм-лейн

`cargo test --features hybrid-local,hybrid-remote` прогоняет все тесты,
которые гейтятся на `hybrid-local` **или** `hybrid-remote`, поэтому
одиночные полные сьюты ничего не добавляли к рантайм-покрытию — только
время (~470 s и ~719 s на прогон). Что действительно требует сборки без
второй фичи — assertions про admission и отсутствующий провайдер; они
оставлены точечными прогонами:

```sh
cargo test --features hybrid-local --test cli_models --test hybrid_config \
  --test hybrid_local --test hybrid_models --test connect
cargo test --features hybrid-remote --test hybrid_config --test config \
  --test hybrid_openrouter
```

Тесты с `#[cfg(not(feature = "hybrid-remote"))]` исполняются в дефолтной
джобе (`linux`), где фич нет вовсе.

## Windows и macOS: исполнять, а не только типизировать

`check --features hybrid-local` доказывает лишь то, что платформенный код
компилируется. Provisioning-код (staging → `rename` → promote, контейнеры
`.staging`/`.old`, `secure_dir`, `available_space`, macOS `codesign`-fixup)
на macOS/Windows до 2026-10-29 не исполнялся вообще. Теперь там гоняется

```sh
cargo test --locked --features hybrid-local --lib
```

Это герметично: все provisioning-тесты идут через `FakeSource`, без сети и
без реальной ORT-библиотеки (она грузится только в `#[ignore]`-лайв-тесте
`tests/hybrid_local_live.rs`), ~2–5 минут на джобу. Так `rename` поверх
существующего файла, права и удаление деревьев проверяются на реальной ФС
той ОС, где они будут работать у пользователя.

Лейн окупился в первом же прогоне (run 40895556715): упали 3 теста, каждый —
из тех классов, что на Linux не видны.

| Тест | Что было не так на платформе |
|---|---|
| `cli::models::tests::fastembed_probe_uncached_model_gives_fetch_hint` | тест писал Windows-путь `C:\Users\...` в TOML basic string → «too few unicode value digits» |
| `hybrid::runtime::tests::promote_runtime_cleans_staging_when_stash_fails` | файл-заглушка на месте бэкапа блокировала `rename` только на Unix: `fs::rename` на Windows = `MoveFileExW` + REPLACE_EXISTING, он заменяет файл каталогом |
| `hybrid::models::tests::fetch_force_refuses_boundedly_when_shared_lock_held` | жёсткая граница 2 s против номинального бюджета ретраев 1 s: на macOS-раннере `sleep(20ms)` в 200 параллельных тестах раздувается вдвое |

Только компиляции (`check --all-targets`) любой из них не ловит —
именно поэтому здесь нужен запуск, а не типизация.

## Кэши: у каждой джобы свой — это осознанно

`Swatinem/rust-cache` включает имя джобы в ключ, поэтому у нас лежат
раздельные записи: `linux` ≈ 654 МБ, `linux-local` ≈ 950 МБ,
`linux-hybrid` ≈ 1.2 ГБ. Один общий ключ (`shared-key`) **не помогает**, и
вот почему:

- Записи кэша в GitHub **иммутабельны**: второй `save` с тем же ключом
  игнорируется, побеждает первый сохранивший. Три параллельные джобы с общим
  ключом → в кэш попадёт `target/` только одной из них, а остальные наборы
  фич потеряют свои артефакты и будут пересобирать зависимости **каждый**
  прогон.
- Разделить «общие зависимости / артефакты крейта» rust-cache не умеет:
  он сохраняет каталог целиком (`registry`, `deps`, `build`, `.fingerprint`).
- Отдельный ключ на джобу даёт каждой джобе стабильный тёплый инкрементальный
  кэш своего набора фич — это и есть причина, по которой линты в `linux`
  занимают 9 s, а не 5 минут.

### Почему не раздавать `target/` артефактом

`cargo test --no-run` в билдер-джобе + `upload-artifact`/`download-artifact`
технически возможны, но: артефакт на 1–1.5 ГБ (upload+download 1–3 мин на
джобу), fingerprint'ы привязаны к абсолютным путям и точной версии rustc, а
переиспользовать один и тот же `target/` между разными наборами фич нельзя —
тест-бинари у них разные. Кэш GitHub отдаёт то же самое быстрее и без ручной
склейки, поэтому «build once, run everywhere» для Rust-тестов мы не делаем.

### Что реально экономит время

1. Combo-сьюта как единственный фичевый рантайм-лейн (минус ~1200 s на PR).
2. Release-прогон `hybrid_ann` (SC-4, panic strategy) — в `nightly`: его
   покрывает `cargo test --locked --release`, а не каждый PR.
3. Отказ от ручной матрицы фич в пользу `cargo hack --depth 2`.

## Тайминги: бюджеты host-relative

CI-раннеры — общие VM и стабильно в 2–2.5 раза медленнее машины разработчика
(измерено 2026-10-29: один и тот же гейт-тест `search_bench` — 6.5 s локально
и 12.5–13 s на `ubuntu-latest`; Rrf p95 13.16 ms в baseline против
26.7–33.0 ms в CI). Отсюда два правила:

- latency-гейт применяет `baseline_p95 × 1.5 × DOCSBASE_BENCH_LATENCY_SLACK + 5 ms`
  (в CI фактор 3, локально 1.0; абсолютный потолок 500 ms не масштабируется) —
  `docs/specs/search-benchmark/requirements.md`, FR-22, Delta 2026-10-29;
- **нельзя ужесточать бюджет по локальному прогону** и нельзя делать вывод
  «код стал медленнее» из красного CI-тайминга.

Таймауты в тестах — тоже бюджеты. Тест, который ждёт асинхронное событие
(вотчер, демон, ANN-билд, IPC), обязан иметь запас на медленный раннер: сейчас
это `watcher_deadline()` в `tests/config_runtime.rs` (60 s на Windows, 20 s на
Unix), бюджет ожидания ANN в `tests/ann_e2e.rs` (300 s на Windows, 60 s
иначе — фоновый билд в debug-бинаре на общем раннере не укладывался в 60 s)
и `wait_until(30s)`-хелперы. Провал таких тестов почти всегда означает
нехватку бюджета, а не регрессию: сообщение обязано печатать, сколько ждали и
в каком состоянии застали систему. Известные флейки и их root cause —
`docs/daemon-test-flakes.md`; стресс-прогон — `flake-stress.yml` (только
вручную, никогда не часть PR).

## Известные пробелы (осознанные)

- Платформенный фичевый код исполняется только в `--lib`-сьюте macOS/Windows;
  интеграционные фичевые сьюты там не гоняются (нет смысла: они проверяют
  registry/cache-логику, не зависящую от ОС, и стоят дорого).
- Лайв-прогон локальной модели (`tests/hybrid_local_live.rs`, `#[ignore]`,
  нужен реальный ORT и скачивание) — вручную, кап по стоимости; воркфлоу
  сознательно не создавался (OQ-3 в `docs/specs/hybrid-local/`).
- macOS-джоба пока advisory (`docs/specs/macos-support`, FR-7).

## Как менять

1. Новая фича → ничего не делать: `--depth 2` покроет пары. Если фич станет
   больше трёх или появится «ядовитая» тройка — снять `--depth`.
2. Новая джоба → обновить таблицу выше и решение о required checks (это
   человеческое действие в branch protection, не в workflow).
3. Новый таймаут в тесте → закладывать минимум ×3 от локального времени
   прохождения, а не «сколько хватило у меня».
4. Иностранный инструмент в CI (`cargo hack`, …) → пиновать версию действия
   и добавить строку в `docs/supply-chain.md` (build actions).
